# 联调与上电检查（bring-up）

> 目标：让"不工作的系统"在**每一步都能被证伪**，而不是一次性接好再猜哪里错。
> 下面的顺序是刻意排的：每一步只引入一个新变量，出错时范围永远是上一步与这一步之间。

## 1. 上电前检查清单

| 检查项 | 为什么 |
|---|---|
| 三个 CAN 节点（A / B / 网关）**共地** | 不共地时差分电平没有共同参考，RX 会收到一堆看起来像噪声的边沿 |
| 总线**两端各一个 120 Ω** 终端电阻 | 少了会反射、多了会让总线负载过重；中间节点不要加终端 |
| 收发器供电按型号给 | TJA1050 是 5 V 器件，3.3 V 供电会使发射器被禁用；SN65HVD230 才是 3.3 V 器件 |
| CAN_H / CAN_L 不要接反 | 接反的典型现象是"完全收不到"，但用万用表量电压又是对的 |
| 网关 GPIO5 → 收发器 TXD、GPIO4 ← RXD | 写反的现象是"发得出去一帧都收不到"（或反之），比编不过更难查 |
| 两个 STM32 节点烧的是**同一份** `protocol.h` | 协议分叉的头号原因；用 `python tools/validate_copies.py` 一步校验 |

## 2. 分步验证顺序

### Step 1：单节点自发自收（不接总线）

把节点设成回环模式（STM32 可临时把 `CAN_MODE` 改为 loopback，ESP32 用 `TWAI_MODE_NO_ACK`），
确认能收到自己发的帧。

> 注意回环自测的盲区：收发共用同一套位定时，**测不出波特率配错**。
> 回环通过只代表"软件链路通"，不代表"能上总线"。

### Step 2：两节点直连（A ↔ B）

只接 A、B 两个节点 + 两端终端电阻，观察：

- A 是否每 100 ms 发 `0x101`（用 CAN 分析仪或 B 的 OLED 计数）；
- B 是否每 1 s 发 `0x102` 与 `0x702`；
- 双方的丢帧计数是否稳定在 0。

若只有一方能收，先看**发送方 TEC**（`CAN1->ESR`）：TEC 持续上涨说明没人 ACK，
问题在物理层或对端没上电，而不是软件。

### Step 3：接入网关

- 网关日志应打印 `TWAI 已启动: TX=GPIO5 RX=GPIO4 250kbps 采样点87.5%`；
- 若网关连不上总线，先把 `CAN_MODE` 改成 `TWAI_MODE_LISTEN_ONLY` 单独验证接收
  （此模式下 `twai_transmit` 直接返回不支持，发不出去是预期行为）；
- 确认 `bus_error_count` 是否有增长：**恒为 0 通常说明 RX 根本没看到线上电平变化**。

### Step 4：网关上云

- 串口日志应出现 WiFi 连接成功、MQTT 连接成功、订阅 `gw0805/+/cmd/#`；
- 用任意 MQTT 客户端订阅 `gw0805/#`，应能看到 `nodeA/telemetry` 与 `gateway/status`。

### Step 5：上位机接入

- 桌面监控台切到"真实网关模式"，应能看到节点 A/B 在线、红外/光敏数值、电机状态；
- 点"电机正转 50%"，执行节点应在 1 s 内回读 `0x102` 显示 PWM=50；
- 点"急停"，执行节点应立即停车，且 `0x102` 的 `flags` 出现急停位。

## 3. MQTTX 手动测试（不经上位机）

订阅 `gw0805/#` 观察上行，向下发命令时注意 **QoS = 1、Retain = 关闭**：

| 想做什么 | 主题 | Payload |
|---|---|---|
| 急停（广播） | `gw0805/all/cmd/estop` | `1` |
| 解除急停 | `gw0805/all/cmd/estop` | `2` |
| B 正转 50% | `gw0805/nodeB/cmd/motor` | `1,50` |
| B 反转 30% | `gw0805/nodeB/cmd/motor` | `2,30` |
| B 停 | `gw0805/nodeB/cmd/motor` | `0` |
| B 目标值 2000 | `gw0805/nodeB/cmd/target` | `2000` |
| B 下 PID 参数 | `gw0805/nodeB/cmd/pid` | `1.5,0.2,0` |
| B 切自动模式 | `gw0805/nodeB/cmd/mode` | `1` |

> 命令主题**绝不能** retained：否则新订阅者一连上就重放历史命令，
> 想象网关重启后立刻执行三天前的"电机正转"。

## 4. 现象 → 判据速查

| 现象 | 首查点 | 判据 |
|---|---|---|
| 发不出去、TEC 涨到 255 后 bus-off | 物理层 | `REC == 0` 且 `TEC` 涨 → 没人 ACK，查终端电阻/供电/对端上电 |
| 能收不能发 | 供电能力 | `TEC` 涨、`REC == 0`、`LEC == 4`（位隐性错）→ 发送时 VCC 被拉塌 |
| 收发全死 | 收发器是否工作 | TX 引脚无电平跳变 → 器件没被正确供电/使能 |
| 报文能看到但数值离谱 | 字节序 | 多字节是否按大端、DLC 是否与 `LEN_xxx` 一致 |
| 偶发丢帧、错误计数干净 | 软件节奏 | 看 `seq` 缺口分布；消费速度跟不上生产（OLED 刷屏、网络阻塞） |
| 网络一抖总线整体"装死" | 任务耦合 | 收帧任务里是否直接调了会阻塞的发布接口 |

完整的四个真实故障排查过程见 [`troubleshooting/`](troubleshooting/)。

## 5. 用主机侧自测做回归

改完协议或命令解析后，先跑（不需要任何硬件）：

```bash
python tools/validate_copies.py   # 四端副本是否一致
python tools/test_contract.py     # 3545 条协议断言
```

这两步通过后再上硬件，能排除掉绝大多数"看起来像硬件问题"的软件错误。
