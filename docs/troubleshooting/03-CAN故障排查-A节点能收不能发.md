# CAN 故障排查实录：A 节点"能收不能发"

> 案例日期：2026-10-13
> 涉及节点：A（STM32F103, 11111）、B（STM32F103, 22222）、网关 GW（ESP32-S3）
> 结论一句话：**A 板的 5V 供电能力不足（通路上压降太大），收发器发送时驱动不足，导致发出去的帧在总线上不合法 → 没有任何节点 ACK → TEC 冲到 255 → bus-off。换成 ST-Link 的 5V 供电后立刻正常。**

---

## 一、症状链（当时看到的东西）

一条 250kbps 的 CAN 总线，三个节点 A / B / GW。总线的"拓扑"本身是通的：

| 关系 | 状态 |
|---|---|
| A 收 B、收 GW | ✅ 完美（REC 恒为 0） |
| B 收 GW、GW 收 B | ✅ 正常 |
| **B 收 A** | ⚠️ 偶尔能收到，但"质量很差" |
| **GW 收 A** | ❌ 全程一帧都收不到 |
| A 发帧的错误计数 TEC | 📈 一路涨到 255 → A 进入静默（bus-off） |
| A 进入静默后 | B 一直显示 A OFF |

**关键的不对称**：A 的**接收完全正常**，**发送几乎全废**。换过 TJA1050 模块、换过杜邦线、确认过 PA11=RX / PA12=TX，全都没用；把收发器供电从 3.3V 改到 5V 后 TEC 涨得**慢了一些**，但没治好。

---

## 二、排查路径：从现象走到根因的一条路

整个排查就是**连续回答四个二选一的问题**，每答对一个，范围就砍掉一半。

```
Q0  是谁的问题？          → A 自己（B↔GW 双向正常，只有 A 单向失败）
Q1  是软件还是硬件？      → 硬件（但先用自检屏把软件可能性彻底钉死）
Q2  帧发出去了吗？        → 发出去了（TEC 在涨 ⇒ 发得出去，只是没人 ACK）
Q3  死在总线的哪一段？    → A 自己发不出去（LEC=4，位隐性错）
Q4  为什么发不出去？      → 供电通路太软：收发器发送时拉不动总线
```

### Q0 —— 先分"谁的问题"

方法：看**双向性**。B↔GW 双向都通，说明总线、终端电阻、波特率、采样点这些**公共部分**都是好的。故障只在 A 参与的**单向**通信上。所以问题在 A（或 A 到总线的这一段），不在总线本身、不在 B/GW 的软件。

> **通用原则**：三节点以上，先用"谁能通谁"画一张矩阵。凡是双向都通的对，其公共基础设施一律排除。

### Q1 —— 先分"软件还是硬件"，但要先做一个能看内部的工具

这一步之前的很多轮都在瞎猜，因为**板子上没有眼睛**。转折点是给 A 的 OLED 加了一块 **CAN 自检屏**，直接把 CAN 硬件寄存器和 HAL 状态打到屏上：

| 显示 | 来源 | 含义 |
|---|---|---|
| `hb` | 软件计数 | 心跳任务跑了多少拍（证明任务在跑） |
| `n` / `hp` | `uxTaskGetNumberOfTasks()` / `xPortGetFreeHeapSize()` | 任务数 / 剩余堆（排除任务没建、堆耗尽） |
| `F` | 自建位图 `g_task_fail` | 每个任务创建是否失败 |
| `ok` | `CAN_Send()` 返回值 | 帧有没有**塞进发送邮箱** |
| `T` | `(CAN1->ESR>>16)&0xFF` | **TEC 发送错误计数** |
| `R` | `(CAN1->ESR>>24)&0xFF` | **REC 接收错误计数** |
| `L` | `(CAN1->ESR>>4)&0x7` | **LEC 最后一次错误码** |
| `E` | `CAN1->ESR & 0x7` | `BOFF \| EPVF \| EWGF` 错误状态标志 |
| `M` | `(CAN1->TSR>>26)&0x7` | 三个发送邮箱的 TME 位（7=全空） |
| `S` | `hcan1.State` | HAL 状态机 |

**一次就把软件钉死了**：`n07`（7 个任务，正常）、`F00`（没有创建失败）、`hp3192`（堆充足）、`S2`（LISTENING，正常）。软件层面没有可查的了。

> **通用原则**：当一个故障"看不见"时，**先造一个能看见的工具**，再开始猜。
> 直接读硬件寄存器（`CAN1->ESR`/`CAN1->TSR`）比任何软件层的日志都可信 —— **硬件不会撒谎**。

### Q2 —— 帧到底发出去了吗

用 `TEC ↑` 而 `REC = 0` 这个组合来判断：

- **TEC 在涨** ⇒ 帧**确实被送到总线上了**（TEC 每发失败一次 +8）。如果压根没发，TEC 会一直躺着不动。
- **REC = 0** ⇒ 接收侧一个错误都没有。

于是得到第一个决定性结论：

> **帧发出去了，但没有任何节点 ACK 它。**

顺带解释了"传感器报文能发出去、心跳很少成功"：两者走的是**同一条链路**，只是传感器帧每秒有 10 次机会、心跳每秒只有 1 次。成功率 10~15% 的链路下，10 次里总有 1~2 次撞上，1 次就大概率撞不上。**不是心跳被队列丢了**（CAN 根本没有发送队列，只有 3 个邮箱，满了就直接丢帧返回 0）。

### Q3 —— 死在总线的哪一段

这是整条路上**最关键的一个判别**，答案就在 `L`（LEC）：

| LEC | 含义 | 说明什么 |
|---|---|---|
| **3** | 应答错 ACK Error | 帧**每一位都发对了、自己也回读对了**，只是没人把 ACK 位拉低。⇒ 断在 **A→总线**（A 自己和收发器 TXD 都是好的） |
| **4** | 位隐性错 | A 发**显性**、回读到**隐性**。⇒ A 的发送**根本没驱动总线**（PA12 没输出 / 收发器发射器没工作 / **供电拉不动**） |
| **5** | 位显性错 | A 发隐性、回读是显性。⇒ 总线被别的节点占死或短路 |
| 0 | 无错 | 从没出过错（那 TEC 就不该涨） |

实际读数是 **`L` 时不时为 4** ⇒ **A 自己发不出去**。范围从"整条总线"缩到"**A 及其收发器这一小块**"。

> **通用原则**：`LEC` 是硬件在每次出错时**自动写进去的**，不需要软件参与，也造假不了。
> **3 和 4/5 就是分界线**：3 说明"往外接断了"，4/5 说明"自己发不出去"。

### Q4 —— 为什么发不出去

到这一步，嫌疑只剩"A 到总线的这一段"，而这一段的候选是：收发器模块、信号线、**供电**。前两个已经被换过了（无效），所以是**供电**。

**机理 —— 这是整件事最骗人的地方：**

> **CAN 收发器的接收侧和发送侧，耗电完全不是一个量级。**

| | 接收侧 | 发送侧 |
|---|---|---|
| 干什么 | 高阻输入，从总线上"看"差分电平 | 把 CANH 拉到 3.5V、CANL 拉到 1.5V |
| 耗多少电 | **几乎为零** | **对 60Ω 终端总线灌几十 mA** |

供电通路（板子到收发器的 VCC/GND 走线）一旦软了：
- **接收不受影响** —— 反正不耗电，电压怎么晃都能看 → **A 收得干干净净（REC=0）**
- **发送立刻崩** —— 显性位一来，几十 mA 一冲，收发器 VCC 塌下去、GND 抬起来 → 显性电平压不到位 → 别人**解不出来** → 不 ACK → TEC +8

发多了 TEC 冲过 255，硬件**强制**把节点从总线上摘下来（bus-off）→ A 静默 → B 显示 A OFF。

**"3.3V → 5V 后 TEC 涨得慢一些"就是半成品证据**：抬高了一点余量，所以变慢了；但通路还是软的，所以没治好。**换成 ST-Link 供电（通路又短又硬）才彻底解决。**

> **通用原则**：`TEC 在涨 + REC=0` 和 `LEC=4` 这两个信号，都指向**物理层**。
> 见到它们就别再翻代码了，**去量电压**。

## 三、关键判别式速查表

下次遇到 CAN 通信问题，按这张表读现象：

| 观察到的组合 | 结论 | 下一步 |
|---|---|---|
| A 收不到任何帧 | 硬件/配置问题 | 查终端电阻、收发器、波特率、引脚 |
| A 收一切正常，**发**不出去 | **收发器还是供电**（本案例） | 量发送瞬间的 VCC/GND |
| `TEC ↑` 且 `REC = 0` | 发出去了，没人 ACK ⇒ **物理层** | 量总线差分电平 |
| `REC ↑` | 是被别人的错误帧带偏 | 查总线上谁在狂发错误帧 |
| `TEC` 冲 255 后不动了 | **bus-off**，节点已脱离总线 | 见下方 ABOM 待办 |
| `LEC=3` | 帧对，没人 ACK | 查 A→总线的 CANH/CANL |
| `LEC=4` / `5` | 线上电平不对 | **物理层**，量供电和差分电平 |
| `ok=0` 且 `M=7` | 邮箱是空的 ⇒ 不是"邮箱满" ⇒ 查 `hcan1.State` | 见下方 State 注释 |
| `ok=0` 且 `M=0` | 三个邮箱全占死 ⇒ 帧发不出去 | 物理层或对端不 ACK，导致邮箱释放不了 |

**几条容易踩的认知坑（这次实际踩过的）：**

1. **"接收过滤器"跟 ACK 无关。** 过滤器只决定"要不要把收到的帧**交给我们应用**"。帧只要 CRC 通过，**硬件一定会拉低 ACK 位**，与过滤器配不配无关。
   ⇒ 所以"GW 全程收不到 A"**不可能是 GW 过滤器没配**，而是连 ACK 都没有。
2. **帧进邮箱 ≠ 发出去了。** `CAN_Send()` 返回 1 只代表"塞进邮箱了"。线上合不合法，软件一点都不知道。
3. **`hcan1.State` 的枚举值随 HAL 版本变。** 本工程（`stm32f1xx_hal_can.h`）是：
   `0=RESET, 1=READY, 2=LISTENING(正常), 3=SLEEP_PENDING, 4=SLEEP_ACTIVE, 5=ERROR`。
   **`S=2` 就是正常运行态** —— 网上"LISTENING=8、2 是 BUSY"的说法来自有 `BUSY/BUSY_TX/BUSY_RX` 那一套的别的版本，这里根本没有。**枚举值一律以本工程头文件为准。**
4. **换模块/换线无效 ≠ 问题在软件。** 很可能是"被换掉的东西本来就没坏，坏的是没被换的那一段"。这次坏的是**供电**，而供电线跟着 A 走，换多少次模块都没用。

## 四、留下的代码待办

物理层修好后，`STM32Project/HAL/ForVsCode/11111/Core/Src/can.c` 里这两个当时"因为物理层坏掉才这么设"的参数应该改回常规配置：

- **`AutoBusOff` : `DISABLE` → `ENABLE`**
  它管的是"**掉线之后能不能自己爬回来**"，不是"要不要掉线"（TEC>255 时掉线是硬件强制的，这个参数拦不住）。
  `DISABLE` 时掉到 bus-off 后硬件置起 `INIT`，而**工程里没有任何地方清 `INIT`** ⇒ **一旦掉线只能手动复位** —— 这正是"静默后 B 一直显示 A OFF"的直接原因。
  当时不改的理由（怕 ABOM=1 让 A 反复"掉线→恢复→刷错误帧"，拖垮当时唯一正常的 B↔GW）现在已经不成立。

- **`AutoRetransmission` : `DISABLE` → `ENABLE`**
  当时设 `DISABLE` 是为了防止物理层坏掉时疯狂重发、更快掉线。物理层好了之后，CAN 的**常规配置是"一直重发到成功为止"**。

另有两处收尾：

- `A_CAN_SELFCHECK` 改回 `0`，恢复第 3 行的网关状态显示（自检屏是占用了那行的）。
- 自检屏 `S` 那一行的行内注释还写着旧的 `8=LISTENING`，跟文件上方的说明块不一致，要改。

**还有一个已知的、与本次故障无关的隐患**：`CAN_Send()` 被两个任务并发调用（`photoAdcTask` 优先级 32 会抢占 `canHeartTask` 优先级 15），在"读 TSR"和"写邮箱"之间没有互斥。竞态窗口只有微秒级，不是本次位错的成因，但属于该修的。方案：给 `CAN_Send()` 加互斥锁，或把所有发送收敛到同一个任务里。

## 五、可复用的排查方向（泛化）

把这次的经验抽出来，下次遇到类似的"节点级通信故障"：

1. **先画连通性矩阵**，用双向性把公共基础设施排除掉。谁双向都通，谁就没问题。
2. **看不见就造眼睛。** 在故障节点上加一块把内部状态（**硬件寄存器优先**）打出来的屏，比猜十轮都值。
3. **用错误计数定位到"哪一段"**，而不是一上来就怀疑代码。
   对于 CAN：`TEC/REC` 告诉你方向和量级，**`LEC` 告诉你死在哪一段**。
4. **注意"不对称故障"。** 一个功能正常、另一个功能全废 —— 先去想这两个功能**在物理上有什么不同**。
   本案例的关键就是：接收不耗电，发送要推几十毫安。
5. **同一段线路上"疑似有问题的东西"要按物理量去量，而不是按直觉去换。** 换件只是排除法，量电压才是定位法。
6. **修正自己的判断时要说出来。** 这次中途把 `hcan1.State` 的枚举值搞错过一次（把别的 HAL 版本的值套上来了），改正后要明确告知，否则别人会拿着错误的标准去追一个不存在的幽灵。

## 附：本次定位用到的硬件事实

- 收发器：TJA1050（真片是 **5V 器件**；3.3V 下发射器被禁用）
- 接线：TXD = PA12（AF_PP）、RXD = PA11（INPUT）、S 脚接地、VCC = 5V
- 终端：总线两端各一个 120Ω，**恰好两个**，量 CANH↔CANL 应为 60Ω
- 总线空闲时 CANH / CANL **各自都应在 ~2.5V**；发送时差分在 0V ↔ ~2V 之间摆
- 波特率 250kbps：APB1=36MHz，Prescaler=9，BS1=13TQ，BS2=2TQ →
  `36M/(9×16) = 250k`，采样点 `14/16 = 87.5%`
