# CAN 故障排查实录：网络抖一下，整条 CAN 侧陪着装死

> 案例日期：2026-10（阶段 1，MQTT 联调期）
> 涉及节点：ESP32-S3 网关（`gw0805`）、A（`11111`）、B（`22222`）
> 结论一句话：**`esp_mqtt_client_publish()` 不是"丢进队列就返回"，它在【调用者的任务】里同步写 socket，而且全程握着 MQTT 的 API 锁，最长等 `network_timeout_ms`（默认 **10 秒**）。而调用它的，正是那个负责收 CAN 帧的任务。网络一卡 10 秒 → 没人排空 TWAI 接收队列 → CAN 帧静默丢弃 → A 被判掉线；紧接着，发心跳的任务又卡在**同一把锁**上 → 0x703 心跳停发 → B 也被判掉线。于是"网络抖一下"变成了"整条 CAN 侧陪着一起装死"。**

---

## 一、症状链（当时看到的东西）

```
I (759855) CAN: 1s 收 3 帧 (累计 1551) | 节点A: 在线 | 节点B: 在线
W (763435) CAN: 节点 A 心跳超时(3000 ms 没消息)，判定掉线
W (770423) transport_base: Poll timeout or error, errno=Success, fd=54, timeout_ms=10000
E (770423) mqtt_client: Writing didn't complete in specified timeout: errno=0
W (770424) MQTT: 与 broker 断开，等待自动重连...
W (770424) mqtt_client: Publish: Losing qos0 data when client not connected
I (770424) CAN: RX 0x102 B状态 motor=0 pwm=0 mode=0 flags=0x00
W (770424) mqtt_client: Publish: Losing qos0 data when client not connected
I (770424) CAN: 1s 收 1 帧 (累计 1552) | 节点A: 掉线 | 节点B: 在线
W (770425) mqtt_client: Publish: Losing qos0 data when client not connected
I (770425) CAN: 节点 A 上线
W (770425) CAN: 节点 B 心跳超时(3000 ms 没消息)，判定掉线
I (770425) CAN: 节点 B 上线
```

| 观察 | 状态 |
|---|---|
| 之前一直好好的（1551 帧，A/B 都在线） | ✅ |
| 网络那侧出现 `timeout_ms=10000` 的 poll 超时 | ❌ **挂了整整 10 秒** |
| CAN 那侧 A 判掉线**早于**网络日志 | ❌ 顺序反直觉 |
| A/B 掉线→上线，间隔只有几毫秒 | ❌ 不是"真掉线"，是**误判** |
| 每次复现，过程一模一样 | ❌ **"总是会同样的过程掉线"** |

**当时最容易走错的两个方向：**

| 怀疑的方向 | 直觉理由 | 为什么错 |
|---|---|---|
| CAN 线/共地有问题 | 两个节点同时掉线，像总线故障 | 总线故障不会**同时**把 MQTT 也打断 |
| 节点 A/B 的固件判活逻辑有 bug | A 掉线了 B 还显示在线，看着像判活代码写错了 | 判活逻辑没错，它只是**排在后面还没轮到** |

> **注意最反直觉的一条：CAN 掉线的日志，比网络超时的日志早了整整 7 秒。**
> 直觉上"网络先出问题，然后连带 CAN"才对。日志顺序反过来，说明**不是网络通知了 CAN，而是同一件事同时掐住了两边**。

## 二、排查路径：从现象走到根因的一条路

```
Q0  两侧同时异常，先找它们"共用"什么？   → 共用的既不是电源也不是总线，是【任务】
Q1  10 秒这个数字是从哪来的？            → network_timeout_ms，esp-mqtt 的写超时
Q2  这 10 秒里 CAN 侧到底停没停？         → 停了：接收任务的汇总日志断了 10.5 秒
Q3  为什么 A 掉线了、B 却还显示在线？     → 判活是同一个循环里的 i=0 / i=1，卡在了 i=0
Q4  收 CAN 帧的任务为什么会去写网络？     → 它在收帧回调里直接调了 mqtt_publish
Q5  为什么这一句能卡住 10 秒？            → publish 是【同步写 + 全程持锁】，不是入队
```

### Q0 —— 两侧同时异常，先找"共用的那个东西"

这是本案例的第一刀，也是最省时间的一刀。

**两个看起来毫不相干的子系统（CAN / MQTT）在同一秒出问题**，可能性只有三种：

1. 有个**共同的硬件**把它们一起干掉了（电源、地、晶振）—— 但这是块单板，不存在
2. 有个**共同的软件资源**被长时间占住（锁、任务、队列）
3. 纯属巧合 —— 但"每次都一样"直接排除了巧合

CAN 和 MQTT 在这块板子上共用什么？**不是硬件，是任务。** 准确地说：

- 收 CAN 帧的 `can_rx_task`
- 发 CAN 心跳的 `can_tx_task`

这两个任务里，**其中至少一个同时也在干 MQTT 的活**。

> **通用原则**：一条日志里两个不相干的模块同时报警，**先去数它们共用了哪些资源**（任务 / 锁 / 队列 / 总线 / 电源），而不是分别去查每个模块。
> "共用的那个东西"往往只有一个，而且它一定在调用链的交点上。

### Q1 —— 先把"10 秒"这个数字钉死

日志里 `timeout_ms=10000` 是**直接印出来的**，这个 10000 就是 esp-mqtt 的写超时：

```c
/* mqtt_config.h:52 */
#define MQTT_NETWORK_TIMEOUT_MS (10000)
```

它决定了**一次网络卡顿最多能把调用者扣住多久**。10 秒，对 CAN 这种 1 秒判活的系统来说，是灾难级的量级。

> **通用原则**：任何"最长阻塞 N 秒"的 API，N 就是这个故障的**放大倍数**。
> 先把这个 N 找出来，再问"这 N 秒里谁在等我"。

### Q2 —— 这 10 秒里，CAN 接收到底停没停？

**决定性的一行日志**：接收任务的每秒汇总。

```
I (759855) CAN: 1s 收 3 帧 (累计 1551)
                       ... 中间空了 10.5 秒 ...
I (770424) CAN: 1s 收 1 帧 (累计 1552)
```

这行日志的标签写着 `1s`，但**真实间隔是 10.569 秒**，而累计只涨了 **1**。

**它自己就是证据**：这行日志打在 `can_rx_task` 循环的末尾 —— 它 10.5 秒没打，就说明 `can_rx_task` 自己被扣住了 10.5 秒，而不是"没数据可收"。

> **通用原则**：留一行"由某个任务无条件周期打印"的日志，等于给这个任务装了一个**心跳探针**。
> 它一旦不打了，你立刻能区分"没数据"和"任务死了"。本案例里，这行探针日志是整条线索的转折点。

### Q3 —— 为什么 A 掉线了、B 却还显示"在线"？

这是最像"判活代码写错了"的一处。真相是判活代码没错，它是**串行处理两个节点**的：

```c
/* can.c:349 —— 由 can_tx_task 每秒调用一次 */
static void can_check_nodes(void)
{
    TickType_t now = xTaskGetTickCount();

    for (int i = 0; i < 2; i++) {          /* ← i=0 是 A，i=1 是 B */
        node_watch_t *n = &s_nodes[i];
        ...
        n->online = false;
        ESP_LOGW(TAG, "节点 %s 心跳超时(%d ms 没消息)，判定掉线", ...);

        char payload[64];
        snprintf(payload, sizeof(payload), "{\"code\":%u,\"extra\":0}", (unsigned)ALM_COMM_LOST);
        pub_telemetry(n->alert_topic, payload);   /* ★ 这里会阻塞 ★ */
    }
}
```

注意 `pub_telemetry()` 在**循环体内部**。所以：

```
循环跑到 i=0（节点 A）
  → 判 A 超时，打印"A 掉线"          ← 日志出现
  → 调 pub_telemetry() 发 A 的告警
     → 撞上已被别人持有的 MQTT API 锁
     → ★ 卡住 7 秒 ★
        （这 7 秒里，循环停在 i=0，B 根本还没被检查到）
  → 解锁返回，继续 i=1
  → 判 B 超时，打印"B 掉线"           ← 日志晚了 7 秒才出现
```

**"A 掉线时 B 还在线"不是判活 bug，是循环卡在了第一圈。** 把时间算术代进去，分毫不差：

| 事件 | 日志时刻 | 推算 |
|---|---|---|
| A 最后被记录到的时刻 | — | `763435 − 3000 = 760435` |
| B 最后被记录到的时刻 | — | `770425 − 3000 = 767425` 之前 |
| **阻塞开始** | — | `770423 − 10000 = 760423` |
| A 判掉线 | 763435 | 阻塞开始后 1 秒 |
| A 的告警发布完成（拿到锁） | 770424 | 阻塞结束 + 1 秒 |
| B 判掉线 | 770425 | 上一条 + 1 秒 |

`760423`（阻塞开始）和 `760435`（A 最后一条心跳）几乎重合，差 12ms —— 那是判活任务 1 秒轮询的相位差。**两件事被钉死在同一个时刻上。**

> **通用原则**：一个任务**串行处理多个对象**（多节点、多通道、多设备）时，**在处理第 i 个对象时阻塞，会让第 i+1..n 个对象全部延迟判活**。
> 表现就是"前一个掉线了，后一个还好好的"—— 看着像每个对象的逻辑不同，其实只是**排队位置不同**。
> 修法：判活/扫描这种循环里**绝不做可能阻塞的 IO**，只置标志位。

### Q4 —— 收 CAN 帧的任务，为什么会去写网络？

看调用链就一目了然了 —— **收帧 → 解析 → 发布，全在同一个任务的栈上**：

```
can_rx_task  (prio 6)
  └─ twai_receive()                       ← 唯一排空 TWAI 接收队列的地方
     └─ can_dispatch(&msg)                ← can.c:414
        ├─ A_SENSOR 分支 → pub_telemetry()  ← can.c:450
        ├─ B_STATUS 分支 → pub_telemetry()  ← can.c:477
        └─ ALARM    分支 → pub_telemetry()  ← can.c:498
                          └─ mqtt_publish()  ← mqtt.c:128
                             └─ esp_mqtt_client_publish()   ← 同步写 socket，最长 10 秒
```

同样地，`can_tx_task` 也有一条：

```
can_tx_task  (prio 4)
  └─ can_send_periodic()   ← 每秒发 0x103 / 0x703 心跳
  └─ can_check_nodes() → pub_telemetry()   ← can.c:376（就是上面 Q3 那处）
```

**两个 CAN 任务，都直接踩着 MQTT 的同步写。** 这就解释了为什么"网络卡"能同时干掉两边。

### Q5 —— 为什么这一句能卡 10 秒？读源码

这里必须先破一个直觉。`esp_mqtt_client_publish()` 这名字听起来像是"投递到某个队列就返回"，**实际上完全不是**：

```c
/* esp-mqtt/mqtt_client.c:2065 附近 */
int esp_mqtt_client_publish(...)
{
    ...
    MQTT_API_LOCK(client);          /* 2078：xSemaphoreTakeRecursive(..., portMAX_DELAY) */
    ...
    while (sending) {               /* 2132 */
        if (esp_mqtt_write(client) != ESP_OK) {
            esp_mqtt_abort_connection(client);
            break;
        }
    }
    ...
    MQTT_API_UNLOCK(client);
}

/* mqtt_client_priv.h:50-56 —— 这把锁是 portMAX_DELAY，无限等 */
#define MQTT_API_LOCK(c)   xSemaphoreTakeRecursive(c->api_lock, portMAX_DELAY)
```

三个致命事实叠在一起：

1. **写 socket 发生在调用者的任务里**（不是 esp-mqtt 内部任务）
2. **全程握着 API 锁**，而且这把锁的等待时间是 `portMAX_DELAY`（无限）
3. **写超时是 10 秒**（`MQTT_NETWORK_TIMEOUT_MS`）

于是网络一卡，第一个进来的 `can_rx_task` 被扣 10 秒；这 10 秒里 `can_tx_task` 也想发（要报 A 掉线），**撞上同一把锁，再扣 7 秒**。

**连锁反应全貌：**

```
WiFi 抖 / broker 不回 ACK
        ↓
can_rx_task卡在esp_mqtt_write里，持锁 10 秒(此时rx被卡住收不到A和B心跳，判断为掉线，要给MQTTX发送mqtt帧要用can_tx_task)
        ↓                                    ↓
没人排空 TWAI 接收队列                 can_tx_task 撞上同一把锁
（depth 5，满了就静默丢帧）              卡 7 秒 → 0x703 心跳停发
        ↓                                    ↓
A 的帧收不到 → 判 A 掉线               B 收不到心跳 → 判网关掉线
        ↓                                    ↓
        └──────────►  A/B 在几毫秒内"掉线又上线"（误判）
```

而且 B 那侧还有**第二重后果**：0x703 网关心跳同时兼任 B 的**电机保活**（B 的电机在转时，3 秒收不到 0x703 就停车）。所以这一卡，**正在转的电机也会停下来**。

> **通用原则**：读一个 API 的语义，**看源码，别从名字猜**。
> `xxx_publish` / `xxx_send` / `xxx_post` 这类名字，底层可能是"入队"（快、不阻塞），也可能是"同步写"（慢、可能阻塞，甚至持锁）。
> 判断标准就一句话：**它有没有在返回到我之前真正把数据送出网络？*
>
> 

**我总结的：**

**网关的收帧任务在收到 A 的遥测后,就地调 `mqtt_publish` 发出去。这个调用是同步的:它在调用者任务里写 socket,而且全程握着 MQTT 的 API 锁。网络一抖,本机 TCP 发送缓冲区被"等不到 ACK"填满,`select` 等 socket 可写等到 10 秒超时才返回 —— 这 10 秒里没人排空 TWAI 接收队列,A 的心跳别人收不到,于是判 A 掉线。**

**同一时间,发心跳的那个任务发现 A 掉线,也要发一条告警,撞上同一把还没放的锁,又等了 7 秒。它卡住的这一圈循环,既让排在后面的 0x703 心跳发不出去,也让排在后面的 B 的判定晚了 7 秒。网络恢复后两个节点几乎同时"上线" —— 因为本来就没真断过。**



### 修法 —— 把"写网络"从 CAN 任务里搬走

**核心思路：CAN 任务只负责"把数据拷进队列"，真正发送交给一个独立的低优先级任务。**

```c
/* can.c:207 —— 【改后】生产者：永不阻塞 */
typedef struct {
    const char *topic;          /* 字面量宏，静态存储，存指针就够 */
    char        payload[96];    /* 调用点栈上的临时缓冲，必须拷 */
} pub_item_t;

static void pub_telemetry(const char *topic, const char *payload)
{
    if (!mqtt_is_connected()) {
        return;
    }

    pub_item_t item;
    item.topic = topic;
    strncpy(item.payload, payload, sizeof(item.payload) - 1);
    item.payload[sizeof(item.payload) - 1] = '\0';

    /* ★ 第三个参数 0 = 队满时【不等】★
     * 这是整个改动的关键：can_rx_task / can_tx_task 在这一行永不阻塞。 */
    if (xQueueSend(s_pub_q, &item, 0) != pdTRUE) {
        s_pub_drop++;           /* 丢帧必须可观测，不能无声 */
    }
}

/* can.c:229 —— 【改后】消费者：全工程唯一会阻塞在 MQTT 上的地方 */
static void can_pub_task(void *arg)
{
    pub_item_t item;
    while (1) {
        if (xQueueReceive(s_pub_q, &item, portMAX_DELAY) != pdTRUE) {
            continue;
        }
        /* ★★ 阻塞点在这一句，最长 10 秒 ★★
         * 但此刻被卡的只有本任务 —— 这正是整个改动的目的。 */
        mqtt_publish(item.topic, item.payload, MQTT_QOS_TELEMETRY);
    }
}
```

任务优先级（`can.c:926-928`）：

| 任务 | 优先级 | 职责 |
|---|---|---|
| `can_rx` | **6** | 排空 TWAI 接收队列（最高，先保证帧不丢） |
| `can_tx` | **4** | 周期帧 + 判活 |
| `can_pub` | **3** | **垫底**，专吃 MQTT 的阻塞 |

**关键不是"加了个队列"，而是"让阻塞的那句话换了个任务栈"。** 队列本身不会帮你干活 —— 如果 `can_rx_task` 自己入队自己出队，它照样卡死。队列只是传送带，**必须另外有一个真实的执行者**。

改完之后，网络再卡 10 秒，代价只是"遥测延迟几秒、丢几帧"，**CAN 的收发和 0x703 心跳完全不受影响**。

> **通用原则**：实时路径上，**只允许有"拷贝 + 入队"这种有界操作**，不允许有任何"可能阻塞任意长时间"的调用。
> 判据不是"它平时快不快"，而是**"它最坏能阻塞多久"**。

## 三、关键判别式速查表

| 观察到的现象 | 结论 | 下一步 |
|---|---|---|
| 两个不相干的模块**同时**报警 | 共用资源问题 | 数它们共用了哪些**任务/锁/队列/电源** |
| 每次复现过程**完全一样** | 确定性调度/锁顺序问题，不是巧合 | 顺着调用链找唯一的交点 |
| 某任务的**周期日志断了 N 秒** | 该任务被阻塞了 N 秒（不是没数据） | 找它阻塞在哪一句 |
| **前一个对象掉线，后一个还好好的** | 串行循环卡在了前一圈 | 检查循环体里有没有阻塞 IO |
| 日志里出现 `timeout_ms=` | 阻塞上限被印出来了 | 拿这个值去对任务周期，看差几个数量级 |
| 掉线→上线间隔**只有几毫秒** | **误判**，不是真掉线 | 查判活对象的"最后更新时刻"是谁在刷 |

**几条容易踩的认知坑（这次实际踩过的）：**

1. **`esp_mqtt_client_publish()` 是同步的。** 名字里没有任何提示，`mqtt_publish` 这层我们自己封装的函数也看不出来。唯一可靠的判断方式是读 esp-mqtt 源码。

2. **"网络问题"不归网络的模块管。** 这次网络卡顿的**真正受害者是 CAN**（收帧停 10.5 秒），而 MQTT 自己只是打了几行警告。**日志里报错的那个模块，不一定是受影响最重的那个模块。**

3. **判活逻辑容易背锅。** "A 掉线了 B 还在线"看起来百分之百是判活代码写错了，实际是**循环阻塞导致的排队延迟**。看代码之前先把时间账算完。

4. **QoS 0 是真的会丢。** `Publish: Losing qos0 data when client not connected` 不是警告级别的提示，是 **esp-mqtt 在明确告诉你"这条数据没了"**。本项目所有遥测都是 QoS 0，所以这段时间的遥测确实丢了——但对遥测来说可以接受，对控制命令不行（控制命令走 QoS 1）。

5. **`portMAX_DELAY` 是个危险信号。** 凡是看到 `xSemaphoreTake(..., portMAX_DELAY)`，就要问一句：**持锁期间会不会做耗时 IO？** 如果会，那这把锁的等待时间**实际上由最慢的那个持有者决定**，是无界的。

## 四、留下的代码待办

   见上面「修法」。`can.c` 的 4 个 `pub_telemetry` 调用点全部改成入队，新增 `can_pub_task`（prio 3）。

2. **⏳ 待做：把 `network.timeout_ms` 从 10000 降到 1000**
   解耦之后这个超时**不再是安全问题**（只影响 `can_pub_task` 自己的延迟），但降到 1 秒能明显改善"网络抖一下遥测积压"的体验。
   注意：它是**全局**超时，不是每次调用的参数，改了会影响所有 publish。

3. **⏳ 待做：`can_bridge_mqtt` 的下行耦合**
   反方向（broker → CAN）跑在 **esp-mqtt 内部任务**上，里面直接 `can_send` → `twai_transmit`，最长等 50ms。
   比上行那个 10 秒小两个数量级，且控制命令很稀疏，暂时判为可接受。**但同样的模式（在错误的任务里做阻塞 IO）已经出现两次了**，值得警惕。

   `TWAI_GENERAL_CONFIG_DEFAULT` 不改就是 5，且 `alerts_enabled = NONE`，队列满时**静默丢帧**（和案例 01 是同一类问题）。
   解耦后 `can_rx_task` 不再长时间阻塞，这个深度的重要性大幅下降，但**"丢帧无声"这一点仍然没解决** —— 应该统计 TWAI 溢出次数。

## 五、可复用的排查方向（泛化）

1. **两个模块同时出问题，先找它们共用的资源。** 不要分别去查每个模块 —— 交点只有一个，而且它一定在调用链上。

2. **"周期日志断了 N 秒"是最便宜的探针。** 让每个关键任务都无条件周期打一行，区分"没数据"和"任务死了"，成本几乎为零，收益是整条线索的转折点。

3. **读 API 的语义要读源码，尤其是网络 IO。** 不知道 `xxx_publish` 是不是同步的，就不要把它放在实时路径上。判断标准：**它返回到我之前，数据真的送出去了吗？**

4. **实时路径上只允许有界操作。** 允许"拷贝 + 入队"，不允许任何"最坏情况无界"的调用。评估标准是**最坏阻塞时长**，不是平均耗时。

5. **判活/扫描这类串行循环，循环体内不能有阻塞 IO。** 否则第 i 个对象的故障会延迟第 i+1..n 个对象的判定，制造出一堆看起来毫无关联的误判。

6. **解耦的代价是必须处理"丢"。** 队满时 `xQueueSend(..., 0)` 会失败 —— **一定要统计这个失败次数**，否则你只是把"无声阻塞"换成了"无声丢包"。

7. **`portMAX_DELAY` 上锁 + 锁内做 IO = 无界等待。** 这类组合要么拆锁，要么保证锁内的操作有界。

## 附：本次定位用到的技术事实

- **`esp_mqtt_client_publish()` 是同步的**：在**调用者的任务**里写 socket，不是投递到队列。见 `esp-mqtt/mqtt_client.c:2065`。
- **`MQTT_API_LOCK` 用的是 `portMAX_DELAY`**：`xSemaphoreTakeRecursive(c->api_lock, portMAX_DELAY)`，无限等待。见 `mqtt_client_priv.h:50-56`（可以用 `MQTT_DISABLE_API_LOCKS` 编译期关掉，但那样会失去线程安全）。
- **`MQTT_NETWORK_TIMEOUT_MS = 10000`**：写超时的来源，也是日志里 `timeout_ms=10000` 的来源。见 `mqtt_config.h:52`。它是**全局**超时，不是每调用参数。
- **`Publish: Losing qos0 data when client not connected`** 是 esp-mqtt 自己打的，位置在 `mqtt_client.c:2176-2177` 的 `cannot_publish:` 标签下。**它出现 ⇒ 这条数据确实被丢掉了**（QoS 0 不做重传）。
- **`transport_base` 这个日志前缀**：`mqtt://`（非 TLS）也走 `transport_ssl.c`，而那个文件的 TAG 就是 `transport_base`。所以看到 `transport_base: Poll timeout` 并不代表你在用 TLS，只是模块复用了同一份代码。
- **TWAI 接收队列默认深度 5**：`TWAI_GENERAL_CONFIG_DEFAULT` 不改就是 5，且 `alerts_enabled = NONE` —— **队列满时静默丢帧**，没有中断、没有计数（和案例 01 的 `osMessageQueuePut` 超时 0 是同一类问题）。
- **0x703 网关心跳兼作 B 的电机保活**：B 的电机转着的时候，3 秒收不到 0x703 就 `Motor_SetSpeed(0)`。所以"网关心跳停发"不只是显示问题，**会真的停车**。这也说明为什么"判活信号"必须是网关心跳（每秒无条件发），而不是"多久没收到电机命令"。
- **FreeRTOS 的 `xQueueSend` 超时参数**：给 0 = 队满立即返回 `pdFALSE`，**不等**。这是把阻塞从生产者转移到消费者的关键手段。
- **判活用的是无符号相减**：`(now - n->last_seen) < pdMS_TO_TICKS(TIMEOUT)`，这样 tick 计数回绕（约 49 天一次）不会误判。见 `can.c:363`。
