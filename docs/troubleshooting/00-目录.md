> 每个案例结构一致：**症状链 → 排查路径（Q0→Qn 逐步二分）→ 判别式速查表 → 代码待办 → 泛化方向**。
>
> **这是面试最能讲的部分** —— 也是简历上"能追问三层"的来源。

| # | 案例 | 一句话根因 | 核心方法 |
|---|------|-----------|---------|
| [01](01-CAN故障排查-OLED刷新拖垮接收节奏.md) | **OLED 刷新拖垮接收节奏** | 每字符 22 次 I2C 事务 → 刷屏 >100ms → 接收队列被灌满 → ISR 丢帧 | 算「生产速率 vs 消费速率 vs 缓冲区深度」 |
| [02](02-CAN故障排查-ESP32网关连不上总线.md) | **ESP32 网关连不上总线** | TJA1050 是 5V 器件却接了 3.3V（发射器被禁用） | 回环自测 → LISTEN_ONLY → 数引脚电平跳变 |

## 四个案例的关系

```
01  丢帧        —— 软件节奏问题（消费跟不上生产）
02  收发全死    —— 器件根本没被正确供电
03  能收不能发  —— 供电能力不足（收发两侧耗电差一个量级）
04  连锁误判    —— 软件耦合问题（一条慢路径，拖住所有实时任务）
```

**01 和 04 都是"软件节奏/耦合"问题，值得对照看 —— 它们是同一个病根的两种表现：**

| | 案例 01 | 案例 04 |
|---|---|---|
| 谁慢 | **消费端**（刷 OLED 太慢） | **旁路**（写网络太慢） |
| 拖累了谁 | 接收队列被灌满 → 丢帧 | 整个接收任务被扣住 → 收不到帧 |
| 症状形状 | **丢帧数稳定在一个量级** | **某任务的周期日志整段消失** |
| 判据 | `seq` 有缺口，但错误计数干净 | 周期探针日志断了 N 秒 |
| 缓冲有没有用 | 有用（消费只是"慢"） | **没用**（消费端是"停"了） |
| 修法 | **优化** —— 把慢 IO 做快（22 次事务 → 4 次） | **解耦** —— 把慢 IO 搬到别的任务去 |

**02 和 03 都是"供电"问题，但表现完全相反，值得对照看：**

| | 案例 02 | 案例 03 |
|---|---|---|
| 症状 | **收发一起死** | **能收不能发** |
| 机理 | 供电电压**低于器件规格** → 发射器被禁用 | 供电**电压对、但通路太软** → 发送时被拉塌 |
| 关键差别 | 器件**压根没工作** | 器件**在工作，但推不动总线** |
| 用的工具 | 数引脚跳变（信号没到） | 读 `ESR` 寄存器（TEC 涨、REC=0、LEC=4） |

> **同一个"供电"词，对应两种完全不同的故障模式。**
> 分界线是：**器件有没有在工作**（引脚有没有活动）—— 这一条用示波器/计数器一测就分开。

## 可复用的通用套路（四个案例共有的）

1. **先分半，再二分。** 每一步都把待查范围砍掉一半，别一上来就到处改。
2. **看不见就造眼睛。** 硬件寄存器、引脚跳变计数、**任务的周期探针日志**，比猜十轮都值 —— **硬件和日志不会撒谎**。
3. **别拿没校过的尺子量。** 先确认测量装置本身可信，再下结论。
4. **"我确定接对了"不能替代一次测量。** 真凶常常是"看起来不可能错"的地方（供电、共地、丝印顺序）。
5. **知道每个工具的盲区。** 回环自测通过 ≠ 通信正常（收发共用位定时，测不出波特率）。
6. **看时钟，不看直觉。** 日志的时间戳排列顺序常常反直觉（案例 04 里 CAN 掉线的日志比网络报错**早 7 秒**）。**先把时间账算出来，再解释因果。**
7. **读 API 的语义要读源码，别从名字猜。** `xxx_publish` 可能是"入队"，也可能是"同步写 + 持锁最长 10 秒"。
8. **一条慢路径能拖垮整个系统。** 评估实时路径上的每一句调用，标准是**最坏阻塞时长**，不是平均耗时。

## 面试怎么讲这四个案例

| 面试官可能问 | 用哪个案例答 |
|-------------|-------------|
| "你遇到过最难查的 bug？" | 任选一个，**重点讲"怎么把范围一步步缩小"**，不要只讲结论 |
| "你怎么区分是硬件还是软件问题？" | **案例 03**：`TEC 涨 + REC=0` ⇒ 物理层；`seq 有缺口但错误计数干净` ⇒ 软件侧 |
| "丢帧怎么排查？" | **案例 01**：先看丢帧的**时间分布形状**，再算三个速率 |
| "CAN 的收和发有关系吗？" | **案例 02**：接收方必须发 ACK，所以**发不出去会连带收不到** |
| "你怎么保证测的东西是对的？" | **案例 02**：回环自测的盲区、"别拿没校过的尺子量" |
| "踩过什么坑？" | **三个模块型号相同但供电要求不同** —— 肉眼看不出来，量一下 VCC 就现形 |
| **"两个模块同时报错，你先查哪个？"** | **案例 04**：先找**共用的那个资源**（任务/锁/队列），别分开查 |
| **"实时任务里能不能调网络 API？"** | **案例 04**：不能。先读源码确认它是不是同步的，再问"**最坏能阻塞多久**" |
| **"怎么把慢 IO 从实时路径上摘出去？"** | **案例 04**：队列解耦 —— 生产者只"拷贝+入队（超时 0）"，另起低优先级任务消费 |
| **"解耦之后丢了数据怎么办？"** | **案例 04**：队满必然丢，所以要**统计丢的次数**；遥测可丢，控制命令必须走 QoS 1 |
