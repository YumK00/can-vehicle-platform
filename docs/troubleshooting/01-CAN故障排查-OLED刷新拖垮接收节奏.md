# CAN 丢帧排查实录：OLED 刷新拖垮了接收节奏

> 案例日期：2026-10（阶段 0 联调期）
> 涉及节点：A（STM32F103, `11111`，发送方）、B（STM32F103, `22222`，接收 + 显示方）
> 结论一句话：**B 板刷一屏 OLED 要上百毫秒（`OLED_ShowChar` 每个字符 22 次 I2C 事务，软件 I2C 全是忙等），接收队列被灌满，中断里只能丢帧。把"逐字节写"改成"批量连续写"（22 次 → 4 次事务）后，丢帧归零。**

---

## 一、症状链（当时看到的东西）

| 观察 | 状态 |
|---|---|
| A 每秒发 10 帧（100ms 周期） | ✅ 帧确实在发 |
| 刚上电的一段时间 | ✅ **一帧不丢** |
| **过一阵之后** | ❌ **稳定丢 13~14 帧，然后一直保持在这个量级** |
| 丢帧是随机还是稳定 | **稳定** —— 不是偶发误码，是有东西**持续跟不上** |

**当时试过、但全都无效的三个方向：**

| 怀疑的方向 | 试了什么 | 结果 |
|---|---|---|
| 电压没供够 5V | 换电源 | 无效 |
| STM32F103 带不动"IIC 屏 + 接收任务" | 换板子 | 无效 |
| 接收任务优先级太低 | 调优先级 | 无效 |

> **注意"一开始不丢、过一阵稳定丢"这个细节 —— 它是整条线索里信息量最大的一句话。**
> 随机误码不会这样：误码从一开始就会随机出现，不会有"前一段时间干净"的窗口。
> **只有"缓冲区逐渐被填满、然后进入稳态"才会呈现这种形状。**

---

## 二、排查路径：从现象走到根因的一条路

```
Q0  丢帧是随机的还是稳定的？   → 稳定 ⇒ 不是误码，是"有东西持续跟不上"
Q1  丢在哪一侧？               → B 的接收侧（A 侧一切自洽）
Q2  是"收不到"还是"来不及收"？ → 来不及收：帧到了，但队列满了被 ISR 丢掉
Q3  队列为什么会满？           → 消费太慢：刷一屏 OLED 的耗时 ≈ 帧到达间隔
Q4  刷屏为什么这么慢？         → 软件 I2C + 每字符 22 次事务（逐字节写）
```

### Q0 —— "稳定"两个字先把"误码"排除了

CAN 在误码场景下的表现是**随机丢**，而且通常会伴随错误计数上涨（TEC/REC 上升）。

这次的表现是：
- 丢帧数**稳定**在一个量级（13~14），不飘
- 而且**前面有一段完全不丢的窗口**

**"稳定 + 有启动窗口"是缓冲区饱和的签名**，不是线路噪声的签名。这一条就把排查方向从"电气"整个搬到了"软件节奏"上。

> **通用原则**：丢帧的**时间分布形状**比丢帧的绝对数量更有信息量。
> - 从头就开始随机丢 → 查电气 / 波特率 / 采样点
> - **刚开始不丢、过一阵稳定丢 → 查缓冲区 / 消费速度 / 任务节奏**

### Q1 —— 先分清"是 A 发不出去"还是"B 来不及收"

用**自洽性**判断：如果 A 侧的发送返回值和错误计数都正常，那 A 没问题，问题在 B。

这也是本次第一刀：**别急着看发送方，先确认接收方有没有"收不下"的可能。**

### Q2 —— 队列满时，帧是被"丢掉"而不是"等一等"

关键在 `can.c` 的中断回调里这一行：

```c
/* 超时必须给 0：中断里不能阻塞等队列。 */
(void)osMessageQueuePut(canRxQueue, &frame, 0U, 0U);
```

`osMessageQueuePut` 的超时参数是 **0** —— 意思是"队列满就立刻返回失败，绝不等"。

这是**对的**（中断里绝对不能阻塞），但代价是：**队列一满，帧就静默消失，而且丢掉的是最新那一帧。**

于是丢帧的**唯一来源**就是：

```
帧到达速率  >  帧被消费的速率
        ↓
队列（深度 8）被填满
        ↓
ISR 每收到一帧就丢掉一帧  →  稳态丢帧
```

**"过一阵才丢"到这里完全解释通了**：队列从空到满需要时间，填满之后就进入稳态丢帧。

> **通用原则**：中断里往队列塞东西，**超时必须给 0**；但一旦给了 0，就必须另外**统计"塞失败"的次数**，否则丢帧是无声的。
> 这个案例里，丢帧是靠 CAN 帧里的 `seq` 序列号**间接发现**的 —— 如果帧里没有 `seq`，这个 bug 会一直查不出来。

### Q3 —— 消费为什么慢：把数字代进去

B 的接收任务每收到一帧就要刷 OLED。而**软件 I2C 是忙等的** —— 刷屏期间这个任务不主动让出 CPU，就是纯耗时间。

把两边的数字摆一起：

| 项 | 数值 |
|---|---|
| 帧到达周期 | **100 ms**（A 每 100ms 发一帧） |
| 刷一屏 OLED 的耗时（**优化前**） | **≈100 ms 甚至更多**（见 Q4 的推算） |
| 刷一屏 OLED 的耗时（**优化后**） | **≈23 ms**（这个数字后来写在 `motor.c` 的注释里） |

**优化前：消费速度 10 帧/秒都不到，而生产速度是 10 帧/秒。**
只要消费速度比生产速度**慢哪怕一点点**，队列迟早填满，然后就是"稳定丢"。

> **通用原则**：异步系统的丢帧问题，永远先算这三个数：
> **生产速率、消费速率、缓冲区深度**。
> 只要 `消费 < 生产`，丢帧就是**必然**的，而且**丢多少**由差值决定。

### Q4 —— 刷屏为什么这么慢：每字符 22 次 I2C 事务

问题出在 `OLED_ShowChar` 的写法。**优化前**（逐字节写）：

```c
void OLED_ShowChar(uint8_t Line, uint8_t Column, char Char)
{
    uint8_t i;
    OLED_SetCursor((Line - 1) * 2, (Column - 1) * 8);       // 上半页
    for (i = 0; i < 8; i++)
    {
        OLED_WriteData(OLED_F8x16[Char - ' '][i]);           // 每次事务只写 1 字节
    }
    OLED_SetCursor((Line - 1) * 2 + 1, (Column - 1) * 8);   // 下半页
    for (i = 0; i < 8; i++)
    {
        OLED_WriteData(OLED_F8x16[Char - ' '][i + 8]);       // 每次事务只写 1 字节
    }
}
```

**优化后**（批量连续写）：

```c
void OLED_ShowChar(uint8_t Line, uint8_t Column, char Char)
{
    /* 一个字符占上下两个页，每页 8 字节：
     *   事务1 设光标 → 事务2 写上半页 8 字节
     *   事务3 设光标 → 事务4 写下半页 8 字节
     * 改成这样后，画一个字符只要 4 次 I2C 事务（原来是 22 次）。 */
    OLED_SetCursor((Line - 1) * 2, (Column - 1) * 8);        // 上半页
    OLED_WriteDataSeq(&OLED_F8x16[Char - ' '][0], 8);

    OLED_SetCursor((Line - 1) * 2 + 1, (Column - 1) * 8);    // 下半页
    OLED_WriteDataSeq(&OLED_F8x16[Char - ' '][8], 8);
}
```

**为什么能一次写 8 字节**：SSD1306 在写完一个数据字节后，**列地址会自动 +1**。
所以只要不重新设光标，就能一口气把整页连续写下去 —— 原来的 8 次事务，本质上是在做同一件事，只是每次都重新起停了一次 I2C。

**账算下来**：

| | 事务数 / 字符 | 一屏（约 20 字符） | 相对耗时 |
|---|---|---|---|
| 优化前 | **22** | 440 次事务 | **≈100 ms+** |
| 优化后 | **4** | 80 次事务 | **≈23 ms** |

**事务数降到 1/5.5，刷屏耗时同比例下降。** 消费速度从"跟不上 10 帧/秒"变成"绰绰有余"，丢帧归零。

> **通用原则**：**"事务数"是一个可以数出来的硬指标。**
> 软件 I2C / 软件 SPI / 逐字节 `printf` 这类驱动，最大的性能杀手不是"每个字节多慢"，而是**每个字节都起停一次总线**。
> 优化这类代码，先数事务数，再看能不能合并 —— 收益通常是数量级的。

## 三、关键判别式速查表

| 观察到的现象 | 结论 | 下一步 |
|---|---|---|
| 丢帧**从头就开始、随机分布** | 电气 / 波特率 / 采样点问题 | 量差分电平、核对两边位定时 |
| **开头不丢、过一阵稳定丢** | **缓冲区饱和**（本案例） | 算 生产速率 vs 消费速率 vs 队列深度 |
| 丢帧数稳定在某个量级不飘 | 稳态丢帧，不是偶发误码 | 同上 |
| 错误计数 TEC/REC 一直都在涨 | 物理层问题 | 去量电压 |
| 错误计数干净、但 `seq` 有缺口 | **软件侧丢帧**（队列/邮箱满） | 查生产-消费速率 |

**几条容易踩的认知坑（这次实际踩过的）：**

1. **"电压不够"是最容易怀疑、也最容易白费时间的方向。**
   它和"缓冲区满"的症状在表面上都表现为丢帧，但**时间分布形状完全不同** —— 电气问题不会给你一段"干净的启动窗口"。

2. **"换个更快的板子/更高的优先级"治不好节奏问题。**
   优先级只决定"谁先跑"，不决定"总共只有多少时间"。消费速度不够，提优先级只是让它**更早地发现队列是满的**。

3. **中断里 `osMessageQueuePut` 超时给 0 是对的，但要配套统计。**
   给 0 是为了不阻塞中断（正确），但代价是丢帧无声。**必须自己数"塞失败"的次数**，否则你只能靠数据里的 `seq` 反推。

4. **"刷屏"这件事在嵌入式里从来不便宜。**
   它是**阻塞式 IO + 忙等**的组合，刷新一屏的时间往往和你的实时周期**同一量级**。凡是"数据来了就刷屏"的任务，都要先算一遍刷一屏要多久。

## 四、留下的代码待办

1. **在 ISR 里统计队列塞失败的次数**
   `osMessageQueuePut` 的返回值现在被 `(void)` 丢掉了。应该累加到一个计数器里，和 CAN 的 `seq` 丢帧数**对照看**：
   - 两个数接近 ⇒ 确实是队列满导致的丢帧（本案例）
   - ISR 计数为 0 但有 seq 缺口 ⇒ 丢在总线上/发送侧

2. **给接收队列的深度一个依据**
   现在深度是 8，是拍的。合理的算法是：
   `深度 ≥ 消费单帧最坏耗时 / 帧到达周期`，再留 2 倍余量。
   本案例里：刷一屏 23ms、周期 100ms ⇒ 深度 ≥ 1 就够；但**优化前刷屏 100ms+ ⇒ 深度再大也没用**，
   因为消费速率本身低于生产速率，缓冲区只能推迟崩溃、不能避免。

3. **把"刷屏"从接收路径里摘出去**
   更彻底的做法是：接收任务只管**存数据 + 置标志**，另开一个低优先级任务专门刷屏，
   屏上显示"最新一次的值"而不是"每一帧"。**接收路径上不能有慢 IO。**

## 五、可复用的排查方向（泛化）

1. **先看丢帧的"形状"，再看数量。** 随机 vs 稳定、有没有启动窗口，直接决定去查电气还是查软件。

2. **异步系统丢帧，永远先算三个数**：生产速率、消费速率、缓冲区深度。
   `消费 < 生产` 时丢帧是必然的，缓冲区只能推迟它。

3. **慢 IO 不能放在实时路径上。** 软件 I2C / 软件 SPI / `printf` / 逐字节写，都是隐形的时间黑洞。
   要放在实时路径上，就先量化它**单次最坏耗时**。

4. **优化 IO 驱动，先数"事务数"。** 把逐字节改批量连续写（利用外设的地址自增），收益通常是数量级的。

5. **中断里丢帧必须是"可观测"的。** 队列塞失败要计数；数据帧里要带 `seq`。
   这次如果没有 `seq`，丢帧根本不会被发现。

## 附：本次定位用到的技术事实

- **SSD1306 的列地址自动递增**：写完一个数据字节后列地址 +1，所以不重设光标就能连续写整页。
- **软件 I2C 是忙等的**：事务期间任务不让出 CPU，耗时随事务数线性增长。
- **`osMessageQueuePut` 超时 = 0 的语义**：队列满立即返回失败，**不阻塞、不等待**。中断里必须这样用。
- **CAN 帧里带 `seq` 的价值**：它是**应用层唯一的丢帧证据**。
  CAN 硬件只保证"发出去"，不保证"对方交到应用"。只有序号能暴露中间被丢掉的帧。
- **A 侧参数**：100ms 周期发送，DLC=5（红外 2B + 光敏 2B + seq 1B）。
