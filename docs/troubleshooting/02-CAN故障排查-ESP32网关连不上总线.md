# CAN 故障排查实录：ESP32 网关连不上总线

> 案例日期：2026-10（阶段 0 联调期）
> 涉及节点：网关 GW（ESP32-S3，TWAI 控制器）、对照节点（STM32F103, `22222`）
> 结论一句话：**根因不在软件，而在收发器供电 —— TJA1050 是 5V 器件（VCC 4.75~5.25V），却被接了 3.3V。3.3V 下它的发射器被禁用、总线被强制保持隐性，所以既发不出去、也收不到。**
> 顺带挖出一个真 bug：**TWAI 从 BUS_OFF 恢复后落在 `STOPPED` 而不是 `RUNNING`，只调 `initiate_recovery()` 没调 `start()`，永远发不出去。**

---

## 一、症状链（当时看到的东西）

| 观察 | 状态 |
|---|---|
| 上电后第一帧发出去 | ✅ 发出去了 |
| **100ms 之后** | ❌ **`BUS_OFF`** |
| 尝试恢复 | ❌ 恢复后卡在 `ESP_ERR_INVALID_STATE` |
| 切 `LISTEN_ONLY`（只听） | ❌ **连一帧都听不到** |
| `twai_transmit` 返回 | ❌ 无穷无尽的 TX 失败 |

**两个关键的不对称：**

1. **收和发一起废。** 不是"能收不能发"或"能发不能收"，而是**两个方向同时死**。
2. **只听模式也听不到。** `LISTEN_ONLY` 不驱动总线、不发 ACK、对总线**零影响**，
   如果连它都收不到东西，那问题**不可能在"我发得对不对"上**。

---

## 二、排查路径：每一轮都把范围砍一半

```
Q0  问题在 ESP32 侧还是总线侧？   → 回环自测 ── ESP32 侧全好
Q1  是"收"的问题还是"发"的问题？  → LISTEN_ONLY ── 问题在 ESP 之外
Q2  信号到 ESP32 引脚了吗？        → 数 GPIO4 跳变 ── 3 秒 0 次，根本没到
Q3  引脚上挂着什么电平？           → 上下拉探测 ── 恒高，内部下拉拉不动
Q4  为什么收发器不驱动 RXD？       → 查 datasheet ── 3.3V 下发射器禁用
```

### Q0 —— 先用"回环自测"把 ESP32 这半边整个摘掉

**做法**：把 **GPIO5（TX）和 GPIO4（RX）短接**，用自发自收模式测试
（`NO_ACK` + `.self = 1`），不接任何收发器。

**结果：成功。**

**这一步一次性排除了**：TWAI 控制器、GPIO4/GPIO5 引脚、固件、任务、日志链路 ——
**ESP32 这一侧整个是好的。**

**但这里埋了一个后来才点破的坑：**

> ⚠️ **回环自测测不出波特率问题。**
> 因为回环时**收发共用同一个位定时发生器** —— 你用什么位定时发，就用什么位定时收。
> 两边哪怕差 10%，自己跟自己也能对上。**回环通过 ≠ 波特率正确。**
>
> 这个盲区必须记住：回环能证明"控制器和引脚是活的"，**不能证明"你能跟别人通话"**。

### Q1 —— 用 LISTEN_ONLY 把"收"和"发"切开

既然 ESP32 自己是好的，下一步分"发的问题"还是"收的问题"。

**切法**：把控制器切到 `LISTEN_ONLY`（只听模式）。它**只收不发、不发 ACK、对总线零影响**。

| 如果 | 说明 |
|---|---|
| 只听能收到 | 收发器是好的，问题在"发"这一侧 |
| **只听也收不到** | **收发器根本没在工作，或者信号没进来** |

**结果：一帧都收不到。**

因为只听模式**对总线没有任何影响**，所以这一条把"我的发送有没有扰乱总线"整个排除了。
结论很硬：

> **问题彻底在 ESP 之外 —— 收发器、或收发器到 ESP 的连线。**

### Q2 —— 数 GPIO4 的电平跳变（决定性的一锤）

到这一步，与其继续猜，不如**造一个能看见物理现象的仪器**：写一段诊断固件，
**统计 GPIO4 上的电平跳变次数**。

| 结果 | 含义 |
|---|---|
| **3 秒 0 次跳变** | **GPIO4 上的电压一次都没变过** |

这是整条路上最有力的一击：

> **不是波特率问题 —— 信号根本没到引脚，谈不上"解码"。**
>
> 如果信号到了但波特率不对，GPIO4 上**一定会有跳变**（只是解不出来）。
> 0 次跳变意味着：**收发器压根没往这根线上输出任何东西。**

范围从"ESP32 到总线"缩到 **"收发器的 RXD 引脚及其内部"**。

> **通用原则**：`"收不到"` 至少要分成两种：
> **信号没到** vs **信号到了但解不出**。
> 数电平跳变就是区分这两者的最快办法 —— 它比任何软件日志都底层、都诚实。

### Q3 —— 引脚上下拉探测：它在"稳稳地输出高电平"

再进一步：**在 GPIO4 上打开内部下拉，看能不能把电平拉下来。**

| 结果 | 说明 |
|---|---|
| 内部下拉**拉不动**，读回来**恒高** | GPIO4 上**确实挂着东西**，而且那个东西**在主动、稳定地输出高电平** |

这一步把故障范围**夹死在收发器的 RXD 脚两侧**：

- 既然有人稳稳输出高电平 ⇒ **线是通的、引脚是活的**
- 既然它一动不动 ⇒ **收发器没有在"转发总线上的东西"**

剩下的可能只有三种：**收发器没在工作（供电 / 型号不对 / 坏件）**。

### Q4 —— 查 datasheet：TJA1050 的供电电压

翻 TJA1050 的 datasheet：

> **VCC = 4.75 ~ 5.25 V**（它是 5V 器件）
> 在低于规格的供电下，**发射器被禁用，总线被强制保持隐性**。

把这一条和前面量到的现象对起来：

| datasheet 说 | ②③④⑤ 量到的 |
|---|---|
| 发射器禁用 | TX 全失败 → BUS_OFF ✅ |
| 总线强制隐性 | LISTEN_ONLY 也听不到、RXD 恒高、0 跳变 ✅ |

**完全吻合。根因确认：收发器被接了 3.3V。**

## 三、顺带挖出的真 bug：TWAI 从 BUS_OFF 恢复后落在 STOPPED

排查①的时候发现：`BUS_OFF` 之后尝试恢复，恢复完**卡在 `ESP_ERR_INVALID_STATE`**，之后永远发不出去。

这是**代码里的真 bug**，和供电问题是两件独立的事：

> **TWAI 从 `BUS_OFF` 恢复后，状态落在 `STOPPED`，而不是 `RUNNING`。**
> 只调 `initiate_recovery()` 是不够的 —— **必须再调一次 `start()`**。

修复方式：把状态迁移收敛到一个函数里（`can_service_bus_state`），
让它完整走完 `BUS_OFF → RECOVERING → STOPPED → (start) → RUNNING`。

> **通用原则**：**"恢复动作完成"≠"恢复正常工作"。**
> 状态机里的"复位/恢复"往往只是让设备回到"可以启动"的状态，**启动那一步要单独做**。
> 这类 bug 的特征是：**错误被清掉了，功能却没回来。**

### 这里还藏着一条 CAN 的基础事实

> **CAN 的"收"和"发"是耦合的 —— 接收方必须发出 ACK 位，才算收完一帧。**

所以：

- **"发不出去"会连带"收不到"。**
  发帧时如果没人 ACK，发送方会判错、重发、最终 BUS_OFF；而 BUS_OFF 之后节点**完全脱离总线**，收发全停。
- 这也解释了为什么症状是**双向同时死**，而不是单向。

**这条事实的意义**：CAN 上出现"收不到"时，**不要默认是接收侧的问题** —— 也可能是**发送侧坏了把整个节点拖下线**。

## 四、关键判别式速查表

| 观察到的组合 | 结论 | 下一步 |
|---|---|---|
| 回环自测**通过** | 控制器、引脚、固件是好的 | 但**不能**证明波特率正确 |
| 回环**不通过** | ESP32 侧有问题 | 查 TWAI 配置、GPIO、供电 |
| `LISTEN_ONLY` 也收不到 | 问题在**收发器或连线** | 数引脚跳变 |
| `LISTEN_ONLY` 能收到 | 收发器好，是"发"的问题 | 查 TX 路径、ACK、总线被占 |
| **引脚 0 次跳变** | **信号根本没到** | 收发器没在工作（供电/型号/坏件） |
| 引脚**有跳变但解不出** | 信号到了，是**波特率/采样点**问题 | 核对两边位定时 |
| 内部下拉拉不动、读恒高 | 收发器在**稳稳输出高电平** | 查收发器供电和型号 |
| 恢复后卡 `INVALID_STATE` | **状态机没走完**（缺 `start()`） | 补 `start()`，别只 `recovery()` |

**几条容易踩的认知坑（这次实际踩过的）：**

1. **回环自测不是万能证明。**
   它排除了"控制器和引脚是死的"，但**收发共用位定时**这一点，让它在**波特率**上是瞎的。
   `回环通过` 和 `能和别人通话` 是两件事。

2. **"三颗模块型号相同、接线相同"是假象。**
   本次的真相是：**手里两颗是"3.3V/5V 兼容"的型号，借来的第三颗才是真 TJA1050。**
   外观一样、丝印一样、接线一样，**唯独供电要求不同** —— 肉眼完全看不出来。

3. **"我确定接对了"不能替代一次测量。**
   真凶恰恰是"供电电压"这种**看起来不可能错**的地方。前面所有的推理都建立在"我接对了"的假设上，
   而这个假设从来没有被验证过。

4. **只看软件日志会把人带偏。**
   `BUS_OFF` 和 `TX 失败` 看起来全是软件报的错，实际上**软件只是受害者**。
   **要往物理层去找证据**（引脚跳变、电平、VCC）。

## 五、留下的代码待办

1. **`can_service_bus_state()` 要覆盖完整的状态迁移**
   `BUS_OFF → RECOVERING → STOPPED → start() → RUNNING`。
   只调 `initiate_recovery()` 不调 `start()` 会让节点**永远停在 STOPPED**。

2. **bus-off 恢复次数要计数并上报**
   恢复本身是正常的容错行为，但**"一段时间内恢复了几次"是链路质量的指标**，
   应该计入 `gateway/stats` 上报到云端。**没有计数，恢复就是无声的。**

3. **加一块"物理层可观测"的诊断开关**
   本次最有用的工具是"数 GPIO4 跳变"的临时固件。这个能力值得**固化成编译开关**：
   - 平时关闭，不占资源
   - 排查时打开，直接看引脚活不活

## 六、可复用的排查方向（泛化）

1. **先分半，再二分。**
   回环自测先把"ESP32 侧"和"外部总线侧"切成两半；
   再用 `LISTEN_ONLY` 把"收"和"发"切开；
   最后用 RXD 脚把"收发器内部"和"收发器到 ESP 的线"切开。
   **每一步都让下一步只有一半要查。**

2. **让仪器自己证明自己。**
   本来打算先用"自翻转对照实验"校准测量装置再下结论 —— 这个原则对任何调试都适用：
   **别拿没校过的尺子量。**

3. **把"收不到"拆成"没到"和"解不出"。**
   数电平跳变 / 看信号完整性，比反复改波特率快得多。

4. **知道每个工具的盲区。**
   回环自测的盲区是波特率（收发同位定时）—— **通过它，只能证明它覆盖的那部分**。

5. **同一个功能的正反两面，物理特性可能完全不同。**
   本次的"收得到但发不出"（见案例 03）和"收发一起死"（本案例），
   背后是完全不同的机理：前者是供电能力不足，后者是器件根本没被正确供电。

## 附：本次定位用到的硬件/软件事实

- **TJA1050**：5V 器件，**VCC = 4.75 ~ 5.25V**。
  低于规格时**发射器禁用、总线强制隐性**（RXD 恒高、0 跳变）。
- **SN65HVD230**：3.3V 器件（VCC 3.0~3.6V），**pin8 = Rs**，
  必须**接地（≈0V）才是高速模式**；悬空/拉高会进待机，收发全关。
  （这是后来踩到的另一个同位置的坑，见案例 03 的同期排查。）
- **回环自测**：GPIO5↔GPIO4 短接，`NO_ACK` + `.self = 1` 自发自收。
  **盲区：测不出波特率。**
- **`LISTEN_ONLY`**：只收不发、不发 ACK，**对总线零影响**。
  适合用来判断"问题在不在我这一侧"。
- **CAN 的收和发是耦合的**：接收方必须发出 ACK 位才算收完一帧。
  ⇒"发不出去"会连带"收不到"。
- **TWAI 状态机**：`BUS_OFF → RECOVERING → STOPPED → start() → RUNNING`。
  **恢复之后必须再 `start()`。**
- **参考实现**：`component/MiddleWare/CAN/can.c` 的 `can_service_bus_state`。
