# 现实场景包装 · 车间设备监测与能耗网关

> **本文职责**：把「工业边缘智能网关」这套技术，落成一个**真实存在的业务场景**。
> 目的：让任何人（面试官、老师、评委、客户）在 30 秒内明白**这东西装在哪儿、替谁解决什么问题、值多少钱**。
> 相关：入口 `项目总纲.md` ｜ 战略 `智能网关项目-路线规划.md`

## 一、一句话场景

> **把那套「STM32 + ESP32 双 MCU 网关」装进一家小型冲压车间的配电柜里，把车间里 3 台冲床的启停、产量和振动数据采上来；边缘端就地判断设备异常，网络断了先存在本地，网通了自动补传。车间主任在手机上就能看清哪台机器在偷懒、哪台机器快坏了。**

一句话记住的版本（电梯里说的）：

> **「给老机床装一个不联网也能干活的监工。」**

## 二、为什么选这个场景（而不是"智能家居"）

技术项目的场景不能随便编。选它是因为**场景的真实痛点恰好等于你的技术难点**——每一项技术指标都有一个非做不可的业务理由：

| 车间里真实会发生的事 | 逼出来的技术能力 | 你项目里对应的东西 |
|----------------------|------------------|-------------------|
| 车间电磁干扰大，网线被叉车压断、WiFi 被铁皮房屏蔽 | 断网缓存 + 恢复补传 | 环形缓冲、掉电续写、幂等补传（阶段 2） |
| 每台冲床旁边都有变频器，干扰极强 | 现场总线抗干扰 | CAN 差分总线 + TJA1050，250kbps |
| 工时和产量要算钱，少算一分钟就是少算钱 | 数据不能丢 | CAN 序列号丢帧统计（`seq` 已经埋好） |
| 老板不可能为 3 台小机器上工业组态软件 | 低成本、可复制 | 20~80 元的硬件增补，公共 MQTT Broker |
| 模具磨损导致的废品，往往**发现时已废了几百件** | **趋势预警**（小时/天级，**不是安全防护**） | ESP32-S3 Core1 跑 INT8 异常检测 |
| 车间没人会用电脑，更不会刷固件 | 免拆机维护 | BLE 配网 + OTA（阶段 4） |
| 振动数据 100ms 一条，一条 8 字节，一天一条产线几个 G | 数据在边缘压缩成结论 | 不上传原始波形，**只上报"正常/异常 + 异常分数"** |

**结论**：这不是"先有技术再找场景"，而是"这个场景本来就长这样，技术是被它逼出来的"。所以讲得通。

### 但还有一问：为什么不用现成的？

这是面试官问的**第一句话**，比"为什么选这个场景"更常见：

> **"淘宝上几百块的 DTU / 4G 路由器 / 工业网关就能把数据传上云，为什么要你自己做？"**

**答不上这个，第一节的"值多少钱"就是悬空的。**

| 现成方案 | 价格 | 它有什么 | 它缺什么 |
|---------|------|---------|---------|
| **4G DTU** | 200~500 元 | 串口透传上云，装完就能用 | ❌ 只搬运不翻译：**不做协议转换**，每台设备一个 DTU<br>❌ 断网缓存很小，或根本没有<br>❌ 不能跑模型 |
| **工业网关** | 2000~8000 元 | 多协议、宽温、导轨安装、稳定 | ❌ **小厂买不起**<br>❌ 边缘 AI 要另外加钱<br>❌ 要配组态软件，还得有会配的人 |
| **工业 PC + 组态软件** | 3000 元起 | 功能全 | ❌ 更贵、要维护、功耗大 |
| **本项目** | **100 元级/台** | 多协议汇聚 + 断网零丢失 + 边缘推理 | ⚠️ **防护等级、宽温、EMC 都不如工业产品** —— 这点要主动承认 |

**关键差异只有三个词**，而且正好对应项目的三个阶段：

| 差异 | 现成方案为什么做不到 | 对应阶段 |
|------|-------------------|---------|
| **多协议汇聚** | DTU 是"一根线进、一根线出"，不翻译协议 | 阶段 1（Modbus + CAN） |
| **断网零丢失** | 便宜 DTU 缓存很小甚至没有，能做的都很贵 | 阶段 2（缓存 + 补传） |
| **边缘推理** | 全都要另买算力，或者上云 | 阶段 3（INT8 模型） |

**话术**：

> 「便宜 DTU 便宜在**它只搬运、不思考**。我的价值不在硬件，在网关里那三层软件：**协议翻译、断网不丢、边缘判断**。这三件事市面上要么没有，要么贵十倍。」

> ⚠️ **同时要承认边界**：我这个是原型，"防护等级 / 宽温 / EMC 认证"都比不上几千块的工业产品。**说清"我不是要替代工业产品，我是证明这套软件架构能跑通、且成本能压到 100 元级"。**

## 四、信号 → 业务 的翻译表（最关键的一张表）

你手上只有**光敏 + 红外**（+ 可选 MPU6050），要讲成车间业务，必须把物理量翻译成业务量。这张表讲的时候要背下来：

| 现场信号 | 采集方式 | 对应的业务含义 | 业务价值 |
|----------|----------|----------------|----------|
| **光敏（光照强度）** | ADC | 配电柜内指示灯/电机运行灯亮灭 → **机器开/停** | 自动生成开工工时，不再靠手画"正"字 |
| **红外（遮挡计数）** | ADC/GPIO 中断 | 冲头每下一次 → **一次冲压 = 一个产量** | 实时产量，可算节拍、可算稼动率 |
| **MPU6050 振动** | I2C | 冲床机身振动时序 → **模具磨损/轴承劣化的早期征兆** | 边缘 AI 提前预警，避免批量报废 |
| **CAN 心跳 0x701/0x702/0x703** | CAN | 节点在线 → **这台机器的采集是否活着** | 数据可信度，断线立刻知道 |
| **CAN 序列号 `seq`** | CAN | 采集连续性 → **统计数据是否可信** | 工时/产量能拿去算钱的前提 |
| **MQTT `gateway/stats`** | MQTT | 网关自身健康 → **系统是否可运维** | 别人能远程判断"网关是不是死了" |

> **讲法要点**：不要一上来讲"我用了 ADC 采光敏"。要说"**这台冲床的电机运行指示灯，被我用一个 3 块钱的光敏电阻读成了开工时长**"。

## 六、演示剧本（3 分钟，照着演）

评委/面试官不会听你念架构图，要看**能演出来的东西**。四幕：

### 第一幕：正常巡检（30 秒）
- 手遮挡红外传感器 → 手机 MQTTX 上数值立刻跳一下
- 点开关掉光敏的遮光 → 手机上该机器 `online` / 运行状态翻转
- **话术**：「这是 1# 冲床的真实采集数据，从光电信号到手机上，端到端不到 200ms。」

### 第二幕：断网 30 分钟（1 分钟）★ 最有说服力
- 拔掉车间路由器电源（= 网线被叉车压断）
- 继续遮挡红外，制造 20 次冲压
- **话术**：「现在网断了，但数据一条没丢，全在网关的环形缓冲里，掉电也不会坏。」
- 插回网线 → 60 秒内云端条数补齐，且**不重不漏**
- **话术**：「恢复后按时间戳补传，云端做幂等去重。云端总条数 = 设备端总条数。」

### 第三幕：边缘 AI 报警（1 分钟）★ 技术亮点
- 用信号发生器/手动敲击模拟异常振动（或回放一段异常波形）
- Core1 推理 → 上报 `factory/line1/machine2/anomaly`
- **话术**：「波形没上云，上云的只是结论。**推理 〈实测 __ ms〉，模型 〈实测 __ KB〉，INT8 量化后精度只掉 〈实测 __ %〉**——因为车间的网根本传不动原始振动数据。」
- ⚠️ **这三个数字必须在阶段 3 实测之后才填，不许提前编。**
  一旦照着没测过的数字念，就违反 B.11 的铁律一「只换词汇，不换数字」—— 面试官追问"怎么测的"会当场卡住。

### 第四幕：故障自恢复（30 秒）
- 拔掉 CAN 线再插回 → 总线自动恢复，不用重启
- 故意让一个任务死循环 → 看门狗拉回
- **话术**：「车间里没人会重启设备，所以它必须自己活过来。」

## 七、业务指标 ↔ 技术指标（把数字讲成钱）

**这张表是讲给"听不懂 CAN 的人"的。**

| 技术指标 | 技术目标值 | 翻译成业务语言 | 对客户的意义 |
|----------|-----------|----------------|--------------|
| CAN 采集周期 | 100 ms | 每 0.1 秒记录一次机器状态 | 节拍算得准，不冤枉工人 |
| 端到端延迟 | < 200 ms | 机器一动，看板立刻动 | 能当简易联锁/告警用 |
| 应用层丢帧率 | < 0.1% | 1000 次冲压最多错 1 次 | **工时产量能直接拿去算工资** |
| 断网缓存 | 5000 条 / 30 分钟 | 网断半小时不丢数据 | 叉车压断网线不用停产 |
| 恢复补传 | < 60 s | 网通了 1 分钟自动补齐 | 电工不用跑现场 |
| 数据零丢失 | 云端 = 设备端 | 台账和实物对得上 | 月底不扯皮 |
| AI 推理耗时 | < 50 ms | 异常 0.05 秒内被抓住 | 早一步停机，少废一批活 |
| 模型内存 | < 300 KB | 网关不用换更贵的芯片 | 单台改造成本压得住 |
| 量化精度损失 | < 2% | 预警基本不误报不漏报 | 维修工愿意信它 |
| 连续运行 | 72h，看门狗 0 复位 | 三个班次不用管它 | 装完就能忘掉它 |
| CPU 占用 | < 70% | 还有余量加新功能 | 后续能扩到 6 台机器 |

### 一笔账（讲给老板听）

| 项 | 数字 |
|----|------|
| 单台改造成本 | 硬件约 60~100 元（STM32 最小系统 + TJA1050 + 光敏/红外 + 网关分摊） |
| 一个车间 3 台 | < 500 元 |
| 省下的 | 每月工时争议约 2~4 小时人工核对；一次模具早期预警避免的废品 ≈ 几百元 |
| **回本周期** | **一次成功的模具预警就回本** |

> ⚠️ 这行数字要诚实：**是"避免损失"型的价值，不是"直接创造收入"**。不要说"每月省 5000 元"这种编出来的数字，面试官一追问就崩。

## 八、技术 → 场景 的映射（面试官爱问的"为什么"）

把总纲第四节的设计决策，全部换成车间语言：

| 技术决策 | 车间里的大白话 |
|----------|----------------|
| CAN ID = 功能组(高 7 位) + 节点号(低 4 位) | 「车间现在 3 台机器，将来加到 8 台，我不用改协议、不用改网关代码，改个节点号就行——老板扩产的时候不用再找我。」 |
| 命令类型放 MQTT 主题、payload 放纯数据 | 「网关是个 20 块钱的芯片，内存就那么大，能省一个 JSON 解析器就省一个——省下来的是成本，也是稳定性。」 |
| 心跳不转发到 MQTT | 「3 台机器每秒 3 条心跳，全传到云上是白花流量。网关自己判活，只在状态变化时告诉云端『这台掉线了』。」 |
| 命令主题绝不 retained | 「要是设了 retained，我一重启网关，它就把上次的『停机』命令又执行一遍——车间里这是事故，不是 bug。」 |
| 时间戳由网关补 | 「STM32 上没时钟，它只能说『第 1.2 秒那次冲压』。是网关给它盖了真实时间戳，月底报表才对得上班次。」 |
| 采样点手工对齐 STM32（87.5%） | 「总线上如果采样点差 7.5%，10 帧里就丢 1 帧。对车间来说就是**产量少算 10%**——产线上这是钱。」 |
| 收发器供电必须按型号给（5V） | 「真 TJA1050 接 3.3V，发射器直接被禁用、总线全隐性——**波形看着对，一条数据都发不出去**。这个坑我实测过 RXD 零次跳变。」 |
| 接收用队列而不是全局标志 | 「采集任务和上云任务抢同一个变量，会拼出『1# 机器的产量 + 3# 机器的状态』这种脏数据。**车间统计数据脏了，比没数据更糟**。」 |

## 九、边界与诚实声明（一定要有）

包装不等于编造。**主动划出"什么是真的、什么是模拟的"，反而让人信你。**

| 场景元素 | 真实性 | 说明 |
|----------|--------|------|
| CAN 双节点 + 网关 + MQTT 上行 | ✅ **已实测跑通** | A → CAN → 网关 → MQTTX |
| 光敏 / 红外作为采集源 | ✅ 真实在用 | 现在采的是环境光与遮挡，映射到"机器运行/冲压计数" |
| 丢帧统计、断网缓存、看门狗 | 🔄 阶段 2 待做 | 已有 `seq` 钩子，方案已定 |
| 振动异常检测（MPU6050 + INT8） | ⬜ 阶段 3 计划 | 需加一颗 MPU6050（10~20 元） |
| 冲床本身 | ⚠️ **没有真冲床** | 用传感器时序**模拟**冲床工况；数据是真采的，被监测对象是模拟的 |
| 手机看板 / 云端报表 | ⬜ 阶段 4 | 现在用 MQTTX 手工看，够演示 |
| "装在配电柜里 50℃ 连续跑" | ⚠️ 未做环境试验 | 可以说"面向该工况设计"，不能说"已验证" |

**话术模板**：

> 「现场设备层是真实的 STM32 双节点 + 真实 CAN 总线，数据是我自己采的真实时序；被监测的冲床我用传感器工况模拟——因为这个项目要证明的是**网关的协议、可靠性和边缘计算能力**，不是去机床厂搬一台冲床。硬件架构和软件逻辑，放到真冲床上是一样的。」

## A.1 评分维度说明

| 维度 | 问的是 |
|------|--------|

## A.2 十个场景

### ★★★★★ 场景 1 · 冲压车间设备监测（当前主推）

- **一句话**：给 3 台老冲床装上工时、产量和振动监测，算清工资、提前预警模具磨损。
- **痛点**：工时靠纸画"正"字、月底和工人扯皮；模具磨损到出废品才发现；车间 WiFi 差。
- **光敏**=电机运行灯 → 工时 ｜ **红外**=冲头计数 → 产量 ｜ **振动**=模具/轴承劣化
- **技术上桌**：⭐⭐⭐⭐⭐ ｜ **演示性**：⭐⭐⭐⭐⭐ ｜ **改动成本**：低（加 1 颗 MPU6050）
- **为什么强**：工时和产量直接对应钱，**丢帧率在这里就是"算错工资"**，说服力天然拉满。
- **风险**：老牌学生项目选题，面试官可能见过。**要靠实测数字区分**（见正文第七节）。

### ★★★★★ 场景 2 · 配电房 / 危化品仓储无人值守监测

- **一句话**：在无人值守的配电房或危化品仓库里，监测柜内温度、母排温升、门禁与人员出入，过热或异动就地报警。
- **痛点**：**无人值守 + 不能停机维护 + 出事就是事故**。人工巡检一小时一次，事故发生在两次巡检之间。
- **光敏**=柜内指示灯/弧光 ｜ **红外**=人员/物体闯入计数 ｜ **振动**=变压器/风机异常
- **技术上桌**：⭐⭐⭐⭐⭐ ｜ **演示性**：⭐⭐⭐⭐ ｜ **改动成本**：低
- **为什么强**：**这是唯一一个"看门狗和断网缓存是刚需而不是加分项"的场景**——无人值守的地方没人会去重启设备，网络也常常不通。安全责任话题天然严肃，不会被当玩具。
- **风险**：真做安全类产品要资质（消防/防爆认证）。**话术要限定为"监测与预警，不替代保护装置"**，别说"我做消防"。

### ★★★★★ 场景 3 · 冷链冷库 / 药品储运温控监测

- **一句话**：冷库和冷藏车里的温湿度数据必须**全程不断、可追溯**，断链就是整批货报废。
- **痛点**：**法规强制留档**（GSP/GMP、食品安全），温度记录一断，监管抽查直接判不合格；冷库在偏远位置，网络差。
- **光敏**=库内照明/门开关 ｜ **红外**=人员进出/货物过件 ｜ **振动**=压缩机健康
- **技术上桌**：⭐⭐⭐⭐⭐ ｜ **演示性**：⭐⭐⭐⭐ ｜ **改动成本**：中（需换温度传感器）
- **为什么强**：**断网缓存和"数据零丢失"在这里是法规要求，不是技术炫技**——补传后"云端条数 = 采集条数"直接对应"这批药能不能卖"。这是把可靠性做成了合规价值。
- **风险**：核心量是温度，光敏/红外只是配角；要额外讲清传感器的替换。

### ★★★★☆ 场景 4 · 电梯 / 扶梯远程监测与维保

- **一句话**：给电梯装监测节点，采集运行次数、开关门次数与曳引机振动，维保公司远程判断哪台该保养了。
- **痛点**：**特种设备有强制维保周期**，维保公司按"公里数"式粗略周期上门，成本高；困人故障要立刻知道。
- **光敏**=轿厢照明/平层指示 ｜ **红外**=乘梯人次/门区遮挡 ｜ **振动**=曳引机轴承劣化
- **技术上桌**：⭐⭐⭐⭐⭐ ｜ **演示性**：⭐⭐⭐⭐ ｜ **改动成本**：中
- **为什么强**：**"按状态维保"（CBM）是教科书级的预测性维护故事**，AI 部分站得极稳；振动数据真实、有意义；法规话题加分。
- **风险**：涉及特种设备安全，措辞必须谨慎（**只说"辅助监测"，绝不说"控制电梯"**）；真机改造碰不得，只能讲方案。

### ★★★★☆ 场景 5 · 空压机 / 水泵 / 风机预测性维护

- **一句话**：厂里的公用动力设备（空压机、水泵、风机）常年 24 小时转，用振动监测提前发现轴承故障。
- **痛点**：**非计划停机损失按分钟算**（整条产线等一台空压机）；轴承从异常到损坏有几天到几周的窗口期，正好够预警。
- **光敏**=运行指示灯 ｜ **红外**=转速/启停计数 ｜ **振动**=**主角**，轴承/不平衡/不对中
- **技术上桌**：⭐⭐⭐⭐⭐ ｜ **演示性**：⭐⭐⭐⭐ ｜ **改动成本**：低
- **为什么强**：**这是 MPU6050 + INT8 异常检测最"名正言顺"的场景**——振动信号在工业上有公认的物理意义，AI 不是硬凹的。技术深度最扎实，且不需要"冲床"这种大设备。
- **风险**：演示效果不如"遮挡一下就出数字"直观，需要靠波形图说话。

### ★★★★☆ 场景 6 · 生产线节拍 / OEE 与停机归因

- **一句话**：在装配线或包装线上，自动统计节拍、稼动率和停机时长，分析"今天到底停了几次、为什么停"。
- **痛点**：**OEE 是制造业最通用的管理指标**，但中小厂全靠班组长手工填表，数据假、滞后。
- **光敏**=工位指示灯/设备状态 ｜ **红外**=过件计数 ｜ **振动**=可选
- **技术上桌**：⭐⭐⭐⭐ ｜ **演示性**：⭐⭐⭐⭐⭐ ｜ **改动成本**：很低（现有硬件直接讲）
- **为什么强**：**几乎不用改硬件**，把现有光敏+红外换个讲法就是"节拍与稼动率采集"。OEE 这个词管理层一听就懂，简历上很专业。
- **风险**：技术含量被业务名词掩盖，**必须把丢帧率讲成"数据可信度"才能体现深度**，否则显得只是做了个计数器。

### ★★★☆☆ 场景 7 · 宿舍 / 实验室违规电器与用电安全监测

- **一句话**：监测宿舍或实验室的用电功率、违规大功率电器和潜在的线路过热，超限就告警。
- **痛点**：学校**消防责任极重**，违规电器屡禁不止，人工查寝效率低还容易起冲突。
- **光敏**=环境照度（判断是否有人） ｜ **红外**=人员出入 ｜ **振动**=不用
- **技术上桌**：⭐⭐⭐⭐ ｜ **演示性**：⭐⭐⭐⭐ ｜ **改动成本**：中（需加电流互感器）
- **为什么强**：**校园场景你自己就是用户**，痛点亲身体会、能真落地；"边缘 AI 识别电器类型（看功率波形的小波特征）"是很有亮点的技术延伸，**比异常检测更难、更值得讲**。
- **风险**：**CAN 总线在这里不太自然**（宿舍布线走 CAN 有点怪），需要解释成"楼内设备总线"。

### ★★★☆☆ 场景 8 · 光伏电站 / 充电桩远程监测

- **一句话**：偏远的光伏阵列或充电桩，把发电量、设备状态和故障码采上来，站点没人值守、网络还不稳。
- **痛点**：**站点分散且偏远**，运维上门成本高；网络差（正好是断网缓存的主场）；发电量直接等于收入。
- **光敏**=**照度→发电能力对照**（很自然！） ｜ **红外**=车辆/人员到位 ｜ **振动**=支架/风机
- **技术上桌**：⭐⭐⭐⭐⭐ ｜ **演示性**：⭐⭐⭐ ｜ **改动成本**：中
- **为什么强**：**光敏在这里是主角而不是代用品**——辐照度本来就是光伏的核心参数，"光照 → 理论发电量 vs 实际发电量"的偏差分析非常有说服力；偏远断网让缓存补传成为刚需。
- **风险**：真实演示需要光伏板/充电桩，**很难当面演**，只能靠数据讲故事。

### ★★★☆☆ 场景 9 · 楼宇照明与工位管理（节能）

- **一句话**：办公室按人来自动开灯、人走自动关灯，顺带统计会议室和工位的真实使用率。
- **痛点**：**电费可量化**、空置工位浪费、物业想拿节能数据做汇报。
- **光敏**=环境照度 → 自动调光 ｜ **红外**=人员进出计数 ｜ **振动**=不用
- **技术上桌**：⭐⭐⭐ ｜ **演示性**：⭐⭐⭐⭐⭐ ｜ **改动成本**：低
- **为什么强**：**演示最直观、门槛最低、节能比例算得出来**（"空置关灯省了 30% 照明电"），适合非技术的评委或课程答辩。
- **风险**：**容易被归类为"智能家居玩具"**，技术深度最难体现，AI 部分基本用不上。**如果听众是技术面试官，不推荐。**

### ★★☆☆☆ 场景 10 · 农业温室 / 大棚环境控制

- **一句话**：温室里累积光照、控制补光和通风，让作物长得好一点。
- **痛点**：农户没技术、大棚在田里**网络天生就差**；补光通风靠经验。
- **光敏**=**光照累积量（DLI）→ 补光决策**（很自然） ｜ **红外**=植株/人员 ｜ **振动**=风机水泵
- **技术上桌**：⭐⭐⭐ ｜ **演示性**：⭐⭐⭐ ｜ **改动成本**：中（还要防水防尘）
- **为什么强**：光敏是主角，光照累积量指标真实存在；田间断网让缓存有意义；故事朴实讨喜（助农题材在比赛里加分）。
- **风险**：**边缘 AI 和时间序列异常检测在农业里意义最弱**——你那套"异常检测"硬塞进来会很别扭。**如果阶段 3 是你的简历核心，别选这个。**

## A.4 怎么选：三条判断法则

**法则一：先问"这里的断网缓存是不是刚需"**
如果答案是"断了也没关系"，这个场景就撑不起你的核心卖点。→ **场景 2、3、4、8 是刚需**，1、5、6 是强需求，9 是可有可无。

**法则二：再问"这里的异常检测有没有物理意义"**
如果 AI 是硬塞的，面试官一问"为什么这里需要 AI"就崩。→ **场景 1、4、5 的振动信号最有物理意义**，7 的用电波形次之，**9、10 基本没有**。

**法则三：最后问"我能不能当面演出来"**
不能演的指标等于没有指标。→ **场景 1、6、9 最好演**，2、3、4、5 靠数据演，8、10 基本只能讲。

### 我的建议

| 你的目标 | 选哪个 |
|----------|--------|
| **投嵌入式/MCU 岗，要技术深度** | **场景 1（冲压车间）** 或 **场景 5（空压机预测性维护）** —— 振动 + AI + 可靠性全都能讲 |
| **投工业互联网/IoT 岗，要行业味** | **场景 6（OEE 节拍）** 主、场景 1 辅 —— OEE、稼动率、停机归因是行业黑话，很加分 |
| **课程设计/答辩，评委不全是技术** | **场景 9（楼宇照明）** 或 **场景 2（配电房）** —— 前者好演，后者够严肃 |
| **参加创业/创新比赛** | **场景 3（冷链）** 或 **场景 7（宿舍用电）** —— 一个讲合规刚需，一个讲校园真实痛点，都容易拿分 |
| **想避开"老牌学生选题"** | **场景 2（配电房无人值守）** 最不常见，且看门狗/断网缓存/安全责任三条都硬 |

### 最强的组合打法

> **主线讲场景 1（冲压车间），把场景 5 的振动预测性维护作为技术纵深，把场景 2 的"无人值守"作为可靠性动机。**

这样三个场景各自负责一块：**场景 1 负责业务可信，场景 5 负责技术深度，场景 2 负责说明"为什么可靠性非做不可"**。面试时按追问方向切换——问业务答 1，问 AI 答 5，问可靠性答 2。**一套代码，三套说辞，这是网关类项目最大的优势。**

## A.5 换场景时唯一要改的东西

代码一行不用改，只改**一张翻译表**（就是正文第四节那种）。以场景 2（配电房）为例：

| 现场信号 | 冲压车间里是 | 配电房里是 |
|----------|--------------|------------|
| 光敏 | 电机运行灯 → 工时 | 柜内指示灯/弧光 → 异常发光 |
| 红外 | 冲头计数 → 产量 | 人员/物体闯入 → 非法进入 |
| 振动 | 模具磨损 | 变压器/风机异常 |
| 心跳超时 | 这台机器掉线了 | 这个柜子的监测节点失联 |
| 丢帧率 | 工时算得准不准 | **记录完整不完整（安全追溯）** |
| AI 告警 | 该换模具了 | 该去检查了 |

> **网关类项目的本质优势就在这**：换一个行业，只换一层词汇，底层协议、可靠性机制、边缘推理架构全部复用。
> 面试时把这句话说出来，比多讲三个功能更有说服力——**它证明你做的不是某个行业的定制件，而是一个通用基础设施。**

# 附录 B · 进阶场景菜单（再 9 选 1，CAN 原生行业）

> **附录 A 的 10 个场景偏"通用工业"**，CAN 在里面是"一个合理的选择"。
> **这一批偏 CAN 原生行业**，CAN 在里面是"行业本来就长这样"——技术正当性更强，讲出来更难被质疑。
>
> **适合谁看**：当你知道要投哪家公司（车企、Tier1、港口、电网、机器人）时，**直接用那个行业的场景，比用冲压车间更能引起共鸣**。

## B.0 这批场景多出来的五个讲点

相比附录 A，这批场景能让你的项目显得**更专业**，因为它们各自强调了不同的技术维度：

| 新维度 | 是什么 | 在哪些场景里能讲 |
|--------|--------|------------------|
| **多总线架构** | 网关同时挂**两条 CAN**（不同速率/不同用途），做跨网段转发 | B1 商用车、B5 工程机械 |
| **CANopen 协议栈** | 不止裸 CAN 帧，还有对象字典、PDO/SDO、NMT 状态机、心跳 vs 节点守护 | B3 消防主机、B4 港口 AGV、B6 机器人 |
| **功能安全话题** | 故障导向安全、安全状态、失联降级 | B3 消防、B5 工程机械 |
| **车载/移动环境约束** | 宽压、振动、宽温、熄火后低功耗 | B1 商用车、B9 赛车 |
| **国标合规驱动** | 不是"想不想做"，是法规要求必须做 | B2 换电储能、B7 水气表 |

> **讲法**：这些维度是**附录 A 给不了的深度**。附录 A 讲"我做了个网关"，附录 B 讲"我做了个**符合行业规范的**网关"。

## B.1 ★★★★★ 新能源商用车 / 冷藏车数据网关

- **一句话**：给物流车队的货车和冷藏车装一个车载网关，把**底盘动力 CAN** 和**车厢冷机 CAN** 两路数据打通，车队调度和冷链合规一起解决。
- **痛点**：车队老板看不到每台车的位置、油耗/电耗和冷机状态；**冷链还要证明"全程没断链"**（法规留档）；货车跑在山区高速上，信号时断时续。
- **信号映射**：**动力 CAN**=车速/转速/油门/电池 ｜ **冷机 CAN**=厢温/压缩机状态 ｜ 光敏=厢门开关 ｜ 红外=装卸计数
- **技术上桌**：⭐⭐⭐⭐⭐ ｜ **演示性**：⭐⭐⭐⭐ ｜ **改动成本**：中
- **为什么强**：
  - **车辆本身就是 CAN 总线**，你不需要解释"为什么用 CAN"——这是全场最容易讲通的场景
  - **双 CAN 网关是真实存在的产品形态**（T-Box），你的双 MCU + 双总线架构天然对应
  - **山区隧道里断网是常态**，断网缓存和补传在这里是刚需中的刚需
- **风险**：真车改装涉及车辆安全，**只能做"只读监听"，绝不能写总线**（话术必须限定"数据采集网关，不参与车辆控制"）。

## B.2 ★★★★★ 换电站 / 储能柜 电池包监测

- **一句话**：给换电站的电池包或储能柜做监测网关，采集每个电池包的温度、电压、SOC，异常就地判断并上报溯源平台。
- **痛点**：**电池溯源是国标强制要求**（动力电池回收利用溯源管理）；储能柜热失控是毫秒级事故；换电站分散、无人值守。
- **信号映射**：**BMS 的 CAN**=电池包电压/温度/SOC ｜ 光敏=柜内指示灯/烟雾 ｜ 红外=人员操作
- **技术上桌**：⭐⭐⭐⭐⭐ ｜ **演示性**：⭐⭐⭐ ｜ **改动成本**：中
- **为什么强**：
  - **BMS 与整车/储能系统的通信就是 CAN**，且是行业标配，技术正当性满格
  - **"热失控预警"是安全性话题**，比"节能"严肃得多
  - **储能是当下最热的赛道之一**，简历上出现这个词的加分很高
- **风险**：涉及高压安全，**话术要限定"只做监测与预警，不替代 BMS 的保护功能"**；演示只能靠数据，不能碰真电池。

## B.3 ★★★★☆ 消防报警主机 / 楼宇 CAN 回路联网

- **一句话**：消防报警主机之间的多回路探测总线本身就是 CAN，用一个网关把楼层各回路的状态汇聚到消防控制室和云端。
- **痛点**：**消防是法规强制、责任到人**；老楼改造要把分散的回路状态集中监控；**消防网络绝不允许"失联了但没人知道"**。
- **信号映射**：探测器回路=CAN 上的节点 ｜ 光敏=指示灯 ｜ 红外=人员/烟感联动
- **技术上桌**：⭐⭐⭐⭐⭐ ｜ **演示性**：⭐⭐⭐ ｜ **改动成本**：中
- **为什么强**：
  - **消防总线用 CAN/CANopen 是真实行业事实**，讲出来非常内行
  - **这是"心跳判活"最有分量的场景**——节点失联在消防里叫"故障未上报"，是重大隐患
  - 能自然引出 **CANopen 的 NMT 状态机与节点守护**，协议深度直接上一档
- **风险**：**消防产品有强制认证（CCCF）**，话术必须写"面向运维监测的旁路网关，不接入火灾报警联动逻辑"。

## B.4 ★★★★☆ 港口 AGV / 自动化仓储分拣网关

- **一句话**：给港口的自动导引车（AGV）或仓库分拣线做车载/设备网关，把驱动和传感器的 CANopen 数据汇聚后无线上传调度系统。
- **痛点**：**AGV 移动中 WiFi 必然切换和丢包**；驱动控制器全是 CANopen；调度系统要实时知道每台车的位置与故障码。
- **信号映射**：AGV 驱动 CANopen ｜ 光敏=循迹/到位检测 ｜ 红外=货物/障碍计数
- **技术上桌**：⭐⭐⭐⭐⭐ ｜ **演示性**：⭐⭐⭐⭐ ｜ **改动成本**：中
- **为什么强**：
  - **移动中必然断网**，这是 AGV 场景的物理事实——你的断网缓存不再是"模拟的"，是**场景自带的**
  - **CANopen 是 AGV 和机器人行业的事实标准**，能讲 PDO/SDO 就比只讲裸帧高一档
  - 港口/物流自动化是热门行业，面试对上号很容易
- **风险**：真 AGV 碰不到，只能讲方案或用小车模组演示。

## B.5 ★★★★☆ 工程机械 / 农机远程监测（挖掘机、拖拉机）

- **一句话**：给挖掘机或拖拉机装远程监测网关，采集 CAN 上的工时、油耗、故障码，设备在工地和田间，网络基本没有。
- **痛点**：**设备租赁按工时收费，工时就是钱**；机器散在各处工地，坏了要派人跑几百公里；农机在田里根本没有网。
- **信号映射**：**J1939 / CAN**=转速、油耗、工时、故障码 ｜ 光敏=作业状态 ｜ 红外=作业计数
- **技术上桌**：⭐⭐⭐⭐⭐ ｜ **演示性**：⭐⭐⭐ ｜ **改动成本**：中
- **为什么强**：
  - **J1939 是工程机械和商用车的标准协议**，讲出来就是内行
  - **"工时=钱"和"设备在没网的地方"两条都是刚需**，可靠性动机比冲压车间还硬
  - 宽压（12/24V）、振动、宽温这些**真实的车载工程约束**，能体现硬件设计能力
- **风险**：同样只能"只读监听"，且演示只能靠数据。

## B.6 ★★★★☆ 工业机器人 / 协作臂 CANopen 网关

- **一句话**：给产线上的工业机器人做 CANopen 网关，把伺服驱动器的状态、报警码和关节振动汇聚上云做健康管理。
- **痛点**：机器人**停机就是整线停机**；伺服报警往往是"已经坏了"才报；减速器磨损的早期征兆藏在关节振动里。
- **信号映射**：**CANopen 伺服**=位置/电流/报警 ｜ 光敏=状态灯 ｜ 红外=节拍计数 ｜ 振动=**减速器健康**
- **技术上桌**：⭐⭐⭐⭐⭐ ｜ **演示性**：⭐⭐⭐⭐ ｜ **改动成本**：中
- **为什么强**：
  - **CANopen 是伺服驱动的主流总线之一**，协议深度直接拉满
  - **关节振动 + 减速器磨损是机器人预测性维护的经典课题**，AI 部分极其站得住
  - 机器人是热门方向，简历关键词好对
- **风险**：真机器人碰不到；要讲清"旁路监听，不参与运动控制"。

## B.7 ★★★☆☆ 城市管网智能水表 / 燃气表集中器

- **一句话**：小区或厂区的智能表计通过 **MBus/RS485/CAN 集中器**汇聚，再做统一网关上传抄表平台。
- **痛点**：**公用事业强制要求**；地下表井信号极差（断网缓存天然刚需）；海量表计的协议五花八门，**需要协议转换**。
- **信号映射**：表计总线上的每个表=一个节点 ｜ 光敏=表井盖开启 ｜ 红外=人员抄表
- **技术上桌**：⭐⭐⭐⭐ ｜ **演示性**：⭐⭐ ｜ **改动成本**：中
- **为什么强**：
  - **"多协议汇聚"是网关最正统的使命**，和你阶段 1 的 Modbus 计划完美衔接（CAN + Modbus + MBus 三协议）
  - 抄表数据是**计费依据**，丢一条就是钱，丢帧统计的意义直接量化
- **风险**：演示性最差；CAN 在表计网络里不如 MBus/RS485 主流，需要解释选型。

## B.8 ★★★☆☆ 机柜微环境 / 变电站辅助监控

- **一句话**：监测机柜或变电站辅助系统的柜内温湿度、门禁、水浸和风机状态，异常就地报警、无人值守。
- **痛点**：**无人值守站点的辅助系统故障往往先于主设备故障**；巡检周期长；机柜过热烧板子的损失远大于一个网关。
- **信号映射**：光敏=指示灯/凝露 ｜ 红外=开门/人员 ｜ 振动=风机
- **技术上桌**：⭐⭐⭐⭐ ｜ **演示性**：⭐⭐⭐ ｜ **改动成本**：低
- **为什么强**：**和附录 A 的场景 2 同源但受众不同**——讲给**电网/IDC 运维**的人听，他们一听就懂"辅助监控"这个词；改造成本最低，现有硬件直接能讲。
- **风险**：与场景 2 高度重叠，**别同时讲，会被当成凑数**。

## B.9 ★★★☆☆ 大学生方程式赛车 / 卡丁车遥测

- **一句话**：给 FSAE 赛车或卡丁车做车载遥测，采 CAN 上的车速、电机/发动机参数和悬架振动，跑完一圈回 pit 自动上传。
- **痛点**：赛车上**实时看数据决定调校**；赛道周围没网、赛车不让停车；数据丢了就等于这一圈白跑。
- **信号映射**：**整车 CAN**=速度/油门/制动/温度 ｜ 光敏=环境光 ｜ 振动=悬架/车身
- **技术上桌**：⭐⭐⭐⭐ ｜ **演示性**：⭐⭐⭐⭐ ｜ **改动成本**：中
- **为什么强**：
  - **FSAE 车队本身就是 CAN 总线重度用户**，如果你在学校车队，这个场景是**现成的真实项目**
  - **"高速移动 + 没网 + 数据不能丢"**，是断网缓存最有画面感的场景
  - 演示性和话题性极强，评委/面试官都会感兴趣
- **风险**：只有你确实在车队才用（**别编**）；技术深度偏采集，可靠性机制要主动往上讲。

## B.11 换场景的最佳时机（最重要的一条）

**场景不是选定的，是随面试对象切换的。** 拿到面试通知或知道要讲给谁听之后，**先查对方是干什么的，然后用他行业的场景**：

| 对方是 | 用哪个场景 | 为什么 |
|--------|-----------|--------|
| **车企 / Tier1 / 商用车** | **B1** 商用车网关 | 双 CAN、T-Box、J1939 全是他们的日常词 |
| **电池 / 储能 / 新能源** | **B2** 换电储能 | 国标溯源、BMS、热失控，直接对口 |
| **港口 / 物流自动化 / AGV** | **B4** 港口 AGV | CANopen + 移动断网，正中靶心 |
| **机器人 / 伺服 / 运动控制** | **B6** 机器人 | CANopen 对象字典就是他们的母语 |
| **工程机械 / 农机 / 租赁** | **B5** 工程机械 | J1939、工时计费、远程诊断 |
| **消防 / 安防 / 楼宇自控** | **B3** 消防主机 | CAN 回路 + 心跳判活 + 功能安全 |
| **电网 / IDC / 数据中心** | **A2 或 B8** 辅助监控 | "辅助监控系统"是行话 |
| **制造企业 / 工厂 IT** | **A1 或 A6** | OEE、稼动率、停机归因 |
| **公用事业 / 表计** | **B7** 管网表计 | 多协议汇聚、计费数据 |
| **不确定 / 通用面试** | **A1 主线 + A5 技术纵深 + A2 可靠性动机** | 三场景分工，见 A.4 结尾 |

### 三条铁律

1. **只换词汇，不换数字。** 场景换了，**推理 38ms、丢帧率 0.03%、5000 条缓存这些实测数字一个都不许动**——一旦为了让场景更"合理"而改数字，就变成了编造。
2. **只读，不写。** 凡是涉及车辆、机器人、消防、电梯、电网的场景，**一律限定为"数据采集与监测"，绝不声称参与控制**。这既是安全边界，也是专业度的体现。
3. **讲一个，藏一个。** 一次面试**只讲一个主场景 + 一个纵深场景**。19 个场景全说出来，只会让人觉得你在罗列概念，而不是真做过一件事。

> **最后一句**：场景数量的价值不在"多"，而在于**你随时能换上对方行业的那一件外套，而里面的身子（协议、可靠性、边缘计算）从来没变**。这个"外套可换、能力不变"的事实本身，就是你项目通用性最好的证明。
