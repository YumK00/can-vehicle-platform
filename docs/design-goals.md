# 一、系统定位与边界

## 1.1 一句话定位

> 向下通过 **CAN 总线**采集现场设备数据，在**边缘侧**完成异常检测，向上通过 **WiFi/MQTT** 上云；
> 具备**协议转换、断网缓存、看门狗自恢复**能力，在**资源受限、网络不可靠、实时性要求**的约束下保证数据不丢。
>
> **场景呈现**：城郊冲压车间配电柜内的设备监测网关（详见 `现实场景包装.md`）。技术实现与该场景解耦。

## 1.2 系统边界

| | 范围 |
|---|------|
| **本系统包含** | 节点 A（采集）、节点 B（执行）、ESP32-S3 网关（转换/缓存/推理）、CAN 应用层协议、MQTT 上行与下行、边缘 AI 推理 |
| **本系统不含** | 云平台业务系统、手机 App 开发、MQTT Broker 的搭建与运维（使用公共 Broker）、上位机数据库 |
| **边界接口** | ① CAN 总线（对现场设备）② MQTT Broker（对云）③ 串口（调试与数据集采集） |

## 1.3 设计约束（硬性前提）

这些是**不可协商的前提**，所有设计必须在此之内完成：

| 约束 | 具体限制 | 对设计的直接影响 |
|------|----------|------------------|
| **MCU 资源** | STM32F103（72MHz / 20KB RAM）+ ESP32-S3（双核 / 512KB SRAM / 8MB PSRAM） | 上云 payload 不用 JSON 解析器；模型必须 INT8 量化且 < 300KB |
| **CAN 带宽** | 250 kbps，单帧最多 8 字节有效载荷 | 超 8 字节必须分包重组；心跳不得全量转发 |
| **网络不可靠** | 车间 WiFi 会断、会抖、会切 AP | 必须有本地缓存 + 恢复补传 + 幂等去重 |
| **现场无人维护** | 设备在配电柜内，无人会重启或刷固件 | 必须有看门狗、bus-off 自恢复、OTA、BLE 配网 |
| **无 RTC** | STM32 无实时时钟，只有相对时间 | 时间戳由网关用 SNTP 对齐的 UTC 补齐 |
| **成本** | 单点改造 < 100 元 | 不引入 Linux 网关、不引入工业组态软件 |
| **总线负载** | 见 4.1 计算，阶段 0~4 峰值 **< 5%** | 预留充足余量，允许后续扩到 8~16 节点 |

# 二、总体设计目标

## 2.1 目标分解（四条主线）

```
                        ┌─────────────────────────────────┐
                        │      设计目标（四条主线）        │
                        └─────────────────────────────────┘
                                       │
        ┌──────────────────┬───────────┴────────┬──────────────────┐
        ▼                  ▼                    ▼                  ▼
   P1 协议转换         P2 实时性            P3 可靠性           P4 边缘智能
   CAN ⇄ MQTT          确定性时延           不丢/自恢复          就地判断异常
        │                  │                    │                  │
   多协议接入          端到端<200ms         断网零丢失          INT8 量化
   Modbus 扩展         丢帧率<0.1%          看门狗0误复位       推理<50ms
```

**P1 协议转换**是项目存在的理由；**P2 实时性**是工业场景的门槛；**P3 可靠性**和 **P4 边缘智能**是简历核心与差异化。

## 2.3 非目标（明确不做）

> **写清楚"不做什么"和写清楚"做什么"同样重要**——防止范围失控。

| 不做 | 原因 |
|------|------|
| 自建 MQTT Broker / 云平台 | 不是能力项，公共 Broker 足够；精力放在边缘侧 |
| Linux 网关 / 树莓派 | 成本与复杂度不划算；本项目的价值在 MCU 侧的受限环境 |
| 功能安全认证（SIL/ASIL） | 学生项目无法承担认证成本；只借鉴**设计风格**（fail-safe、看门狗、错误计数） |
| 真实工业设备的电气改造 | 不碰 220V/380V 强电，传感器与被测对象用低压实测或工况模拟 |
| 手机 App / 微信小程序 | 用 MQTTX + 网页仪表盘替代，够演示 |
| 车辆/机器人/消防等场景的**控制**功能 | 一律限定为"数据采集与监测"，**只读不写**（安全边界） |

## F1 · 现场采集功能（节点 A）

| 编号 | 功能 | 描述 | 验收要点 |
|------|------|------|----------|
| F1.1 | 双通道采集 | ADC 采集红外与光敏，原始值 0~4095，不做事先标定 | 与万用表/示波器读数一致 |
| F1.2 | 周期上报 | 每 100 ms 发送 `0x101`，DLC=5：`B0-B1` 红外(BE)、`B2-B3` 光敏(BE)、`B4` 序列号 | 抓帧间隔稳定；`seq` 递增 |
| F1.3 | 序列号维护 | `seq` 每次发送 +1，**0~255 自动回绕** | 回绕处不产生丢帧误报 |
| F1.4 | 心跳 | 每 1 s 发送 `0x701`，DLC=2：`0xA5` + 计数 | 网关可判活 |
| F1.5 | 超限报警 | 采样值越过阈值时发 `0x011`（报警码 3） | 阈值可配（见 F2.4） |

> **方向约定（易错）**：光敏值**越大 = 越暗**；红外值**越大 = 无遮挡**。文档与代码注释必须一致。

## F2 · 执行控制功能（节点 B）

| 编号 | 功能 | 描述 | 验收要点 |
|------|------|------|----------|
| F2.1 | 电机命令响应 | 收 `0x302`，DLC=3：`B0` 命令（0停/1正转/2反转/3设速）、`B1` 参数（0~100）、`B2` 命令序号 | 7 条下行命令逐条验证 |
| F2.2 | 状态回传 | 周期发送 `0x102`，DLC=4：电机状态、PWM、模式、状态位 | 状态与实际执行一致 |
| F2.3 | 模式切换 | 收 `0x332` 切手动(0)/自动PID(1) | 切模式后行为符合预期 |
| F2.4 | 阈值与目标值 | 收 `0x312` 设置目标光照值（0~4095，ADC 原始值） | 设置后自动模式按新目标调节 |
| F2.5 | PID 参数下发 | 收 `0x322`，DLC=7：Kp/Ki/Kd 各 ×100 的 uint16(BE) + 命令序号；**不允许负数** | 下发后调节效果可观测 |
| F2.6 | 心跳 | 每 1 s 发送 `0x702`，魔数 `0x5A` | 网关可判活 |
| F2.7 | **急停响应** | 收 `0x001`（DLC=1）立即停机，置 `ST_ESTOP` 状态位 | 优先级最高，任何模式下都生效 |
| F2.8 | **命令幂等** | 用 `cid` 命令序号去重，重复命令不重复执行 | 重发同一 `cid` 只执行一次 |
| F2.9 | **命令有效期** | 超时未收到任何命令 → 进入安全状态（停机/保持） | 失联后行为可预测（fail-safe） |

## F3 · CAN 应用层协议功能（三工程共用）

| 编号 | 功能 | 描述 |
|------|------|------|
| F3.1 | **ID 分层分配** | `ID = [功能组(高7位)][节点号(低4位)]`，加节点只改节点号 |
| F3.2 | 功能组划分 | `0x000` 安全 ／ `0x010` 报警 ／ `0x100` 周期 ／ `0x300~0x330` 控制 ／ `0x700` 心跳 |
| F3.3 | 大端编解码 | 多字节高字节在前（同 CANopen / J1939）；提供 `PutU16/GetU16` 内联函数 |
| F3.4 | 长度校验 | 每帧校验 DLC 与 `LEN_*` 宏一致，不一致直接丢弃 |
| F3.5 | **心跳判活** | 三查：ID 对 + DLC 对 + 魔数对；任缺一不算有效心跳 |
| F3.6 | **超时判定** | 心跳超时 **3 s**（心跳周期的 3 倍）→ 节点判离线 |
| F3.7 | **丢帧统计** | 用 `PROTO_SeqLost(new, old)` 计算丢帧数，自动处理 0~255 回绕 |
| F3.8 | 报警帧 | `0x011`/`0x012`，DLC=3：报警码 + 附加数据(BE)；统一报警码定义 |
| F3.9 | 诊断帧（预留） | `0x7E0` 请求 / `0x7E8` 响应，遵循 UDS 惯例 |
| F3.10 | 分包重组（阶段 2） | 超 8 字节数据分包传输，带序号与重组超时 |

## F4 · 网关协议转换功能（ESP32 Core0）

> **定位**：CAN 侧它是普通节点（节点号 3）；MQTT 侧它是**唯一**和云对话的人。全部工作 = **CAN 帧 ⇄ MQTT 互相翻译**。

### F4.1 上行（CAN → MQTT）

| 编号 | 功能 | 描述 |
|------|------|------|
| F4.1.1 | 传感器数据转发 | `0x101` → `gw01/nodeA/telemetry`，`{"ir":..,"ldr":..,"seq":..}` |
| F4.1.2 | 状态帧转发 | `0x102` → `gw01/nodeB/telemetry` |
| F4.1.3 | 报警转发 | `0x011`/`0x012` → `gw01/nodeA|nodeB/alert`，**QoS 1** |
| F4.1.4 | **心跳不转发** | 心跳只刷新内部在线状态，**不直接发 MQTT** |
| F4.1.5 | **在线状态翻转上报** | 仅在 `online` **翻转时**发一次 `nodeX/status`，QoS 1 + **retain=1** |
| F4.1.6 | 网关自身状态 | 每 5 s 发 `gateway/status`：`{"wifi":..,"mqtt":..,"cache":..}` |
| F4.1.7 | 网关统计 | 每 10 s 发 `gateway/stats`：`{"rx":..,"lost":..,"lost_rate":..}`（阶段 2） |
| F4.1.8 | **时间戳补齐** | STM32 无 RTC → 网关用 SNTP 的 UTC 为每条数据补 `ts_gw` |

**设计约束（为什么这么做）**：
- **不上 JSON 解析器**：MCU 侧只做字符串拼接，省代码省内存
- **心跳不转发**：1 Hz × N 节点全转发是浪费；云端只看 `status`
- **telemetry 不 retain**：retain 会让新订阅者收到过期数据

### F4.2 下行（MQTT → CAN）

| 编号 | 功能 | 描述 |
|------|------|------|
| F4.2.1 | 单主题订阅 | 只订 `gw01/+/cmd/#`，一层通配节点 + 多层通配命令 |
| F4.2.2 | 命令映射 | 见下方命令总表，**payload 是纯数据不是 JSON** |
| F4.2.3 | **广播白名单** | 只有 `estop` 允许广播（节点号 0）；其他命令必须指名节点，否则拒绝 |
| F4.2.4 | 命令去重 | 为每条下行命令分配 `cid`，用于接收端幂等 |
| F4.2.5 | 非法输入防护 | 参数越界（如速度 > 100、目标 > 4095）拒绝并告警，不向下透传 |
| F4.2.6 | **命令不 retain** | 发命令时 `retain` 必须为 0，防止重启后重放历史命令 |

**下行命令总表（7 条，全部必须验证）**

| # | 主题 | Payload | 生成 CAN 帧 | 执行者 |
|:--:|------|---------|------------|--------|
| 1 | `gw01/all/cmd/estop` | 任意（建议 `1`） | `0x001` | 所有节点 |
| 2 | `gw01/nodeA/cmd/motor` | `命令,参数` 如 `1,50` | `0x301` | A |
| 3 | `gw01/nodeA/cmd/target` | 数字 如 `2000` | `0x311` | A |
| 4 | `gw01/nodeB/cmd/motor` | `命令,参数` 如 `1,50` | `0x302` | B |
| 5 | `gw01/nodeB/cmd/target` | 数字 如 `2000` | `0x312` | B |
| 6 | `gw01/nodeB/cmd/pid` | `kp,ki,kd` 如 `1.5,0.2,0` | `0x322` | B |
| 7 | `gw01/nodeB/cmd/mode` | `0` 或 `1` | `0x332` | B |

## F5 · 网络与云连接功能

| 编号 | 功能 | 描述 |
|------|------|------|
| F5.1 | WiFi 接入 | STA 模式连接车间 AP，断线自动重连（指数退避） |
| F5.2 | MQTT 接入 | `esp_mqtt_client`，**Client ID 由 MAC 生成**（避免多台冲突互踢） |
| F5.3 | **LWT 遗嘱** | 连接时声明 `gateway/status` 主题的遗嘱：`{"online":false}`，QoS 1 + **retain=1** |
| F5.4 | 断线重连 | 重连后自动恢复订阅；清空重传队列中的过期命令 |
| F5.5 | 网络状态上报 | `gateway/status` 中的 `wifi` / `mqtt` 字段反映真实链路状态 |
| F5.6 | SNTP 时间同步 | 联网后同步 UTC，为数据补时间戳；失步时降级为相对时间并标记 |

**LWT 设计意图**：网关异常断电时无法主动发消息，靠 Broker 代发遗嘱，云端才能在秒级发现"网关没了"，而不是等到超时。

# 四、关键设计决策与理由

> 这些是**会被追问**的决策，也是踩过坑才定下来的。每条都要能答"为什么"。

| # | 决策 | 理由 |
|:--:|------|------|
| D1 | CAN ID = 功能组(高7位) + 节点号(低4位) | 加节点只改节点号；网关收"所有心跳"一个掩码搞定；优先级天然分层 |
| D2 | 命令类型放 MQTT 主题，payload 放纯数据 | MCU 上**不写 JSON 解析器**，省代码省内存 |
| D3 | 心跳不转发到 MQTT | 1 Hz × N 节点全转发是浪费；只在状态翻转时更新 `online` |
| D4 | 命令主题**绝不能** retained | 否则新订阅者一连上就重放历史命令并执行 |
| D5 | 状态主题**必须** retained | 新订阅者要立刻知道当前在线状态，而不是等下一次变化 |
| D6 | 时间戳由网关补 | STM32 无 RTC，只能给相对时间；网关用 SNTP 的 UTC 补齐 |
| D7 | 网关采样点手工对齐 87.5% | `TWAI_TIMING_CONFIG_250KBITS()` 是 80%，与 STM32 差 7.5%，会偶发丢帧 |
| D8 | 收发器供电按型号给，不凭经验 | 真 TJA1050 是 5V 器件，接 3.3V 时发射器被禁用、总线强制隐性（实测 RXD 零跳变） |
| D9 | 接收用队列而不是全局标志 | `volatile` 只防优化不防打断，两个任务抢一个标志会拼出混合数据 |
| D10 | 大端编解码 | 同 CANopen / J1939，与人肉抓包和行业惯例一致 |
| D11 | 只允许 estop 广播 | 广播控制动作危险（"所有节点一起开电机"基本不是想要的），也避免产生未定义 ID |
| D12 | 双 MCU 异构而非单 ESP32 | 实时性、故障隔离、两套链路展示；ESP32 重启时 STM32 仍在采集缓存 |

# 八、一句话记住

> **本系统不是"把数据搬到云上"，而是在资源受限、网络不可靠、实时性要求的环境下，把 CAN 现场数据安全、可靠、有价值地送上去——并且能在边缘自己判断异常。**
>
> 四条主线（协议转换、实时性、可靠性、边缘智能）做透任何两条，这个项目就不是 Demo。
